# knowledge/ ——业务知识库

这里放**稳定、可复用的业务知识**：指标定义、分析方法、数据源含义、判断框架。
读者是需要理解「这个数字是什么意思、该怎么用」的人，不限于开发者。

## 与其他几处的边界

仓库里有四处放文字的地方，名字接近但职责完全不同。**弄混的代价不是乱，而是同一个口径
在两处各写一份，然后悄悄分叉**——分叉之后哪份是对的没有答案。

| 位置 | 职责 | 不该放什么 |
|---|---|---|
| `knowledge/` | 业务知识：指标定义、分析方法、数据源含义、判断框架 | API 契约、开发任务、未实现能力的承诺、客户原始数据 |
| `openspec/specs/` | **当前产品行为与接口契约的权威来源** | 通用行业教程、原始参考材料 |
| `openspec/changes/` | 在研变更的 proposal / design / tasks / spec delta | 已经稳定的行业知识 |
| `docs/` | 本地参考资料、二进制文件、真实报表样本。**由 `.gitignore` 整体排除，不入 Git** | 任何需要团队共享和版本追踪的唯一事实来源 |
| `CLAUDE.md` | 工程约定、架构不变量、「错了不会报错」的实现决策 | 面向业务人员的通用知识文章 |
| `README.md` | 项目入口与各类文档入口 | 大段知识正文或完整规格 |

**单一事实来源**：业务概念只在 `knowledge/` 定义，产品必须如何表现只在 `openspec/` 定义，
工程不变量只在 `CLAUDE.md` 定义。别处要引用就给链接加一句摘要，**不复制正文**。

`docs/` 里的资料只是研究输入。从中得出可复用结论时，提炼结论与来源说明写进 `knowledge/`,
**不要把客户数据、真实搜索词 CSV、报价单、侵权审核表搬进来**，也不要为了「目录统一」把
二进制文件提交进 Git。

## 写一篇新知识文档

### 归档判据

问一句：**这段内容在 KeywordIQ 换一套实现之后还成立吗？**

- 成立（ACoS 怎么算、为什么要和毛利一起看）→ `knowledge/`
- 不成立（`/api/analysis/search` 返回什么、掉榜行为什么恒排在后面）→ `openspec/specs/`
- 是「我们为什么这么写代码」（为什么 `dim_product` 的 UPSERT 带 `IS DISTINCT FROM`）→ `CLAUDE.md`

### 最小结构

按内容需要覆盖，不必凑满：解决什么业务问题 → 核心概念与指标定义 → 公式/单位/数据来源
→ 如何解释与常见误区 → KeywordIQ 使用边界 → 相关知识与对应 OpenSpec 链接。

### 能力状态必须标注

**这是本目录最容易出错、且错了不会有任何报错的地方。** 一篇讲 ACoS、库存周转的文章读起来
像是在描述本产品的能力，而这些指标 KeywordIQ 现在**根本没有数据源**——ABA 报表里没有广告
花费、没有库存、没有成本。读的人会以为平台能算，然后去界面上找一个不存在的功能。

所以凡是可能被读成「产品能力」的指标，用统一语义标注：

| 标注 | 含义 | 在 KeywordIQ 的例子 |
|---|---|---|
| **原始事实** | 当前数据源直接提供 | 搜索词当期排名、是否新词、前三商品槽位的 ASIN/标题/品牌/类目、点击份额、转化份额（均来自 ABA 报表） |
| **计算指标** | 基于明确公式和**已接入**数据计算 | 排名变化、近 7 天/4 周走势、三个历史参照点、掉榜、持续增长词 |
| **外部输入** | 依赖 Seller Central、Amazon Ads、成本台账或第三方 | Sessions、CVR、Buy Box 率、CPC/ACoS/TACoS/ROAS、毛利率、库存周转、IPI |
| **分析建议** | 由多项事实形成的判断，不是数据字段 | 竞争强度评估、选品判断链 |
| **规划能力** | **尚未实现。不得表述成当前功能** | 关键词波动排行（issue #7）、ASIN 反查屏（#38）、外观专利与商标查询（#24 / #25） |

判断某个指标属于哪一档时，**以当前代码和接口为准**，不以「应该有」为准。分不清就去看
`openspec/specs/` 与 `frontend/src/services/analysis.ts` 的 `AnalysisRow`。
