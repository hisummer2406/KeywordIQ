## Why

**直传中断在界面上完全无感。** 关标签页、断网、切后台被杀、分片上传最后一步
`CompleteMultipartUpload` 失败——任何一种，用户都以为文件传上去了，实际什么都没有：
OSS 里没有完整对象，库里没有任何记录，历史屏查不到，连一条失败记录都没有。用户唯一
能做的事是「再传一次」，但他没有任何理由知道该这么做。

原因是批次记录建得太晚。现在整条链是：

```
POST /oss/upload-credentials   只签发凭证，不落任何库记录
   ↓  前端直传 OSS（GB 级字节不经应用服务器，服务端全程不知道进展）
POST /oss/import               到这里才第一次落 ImportBatch
```

直传阶段横跨全过程最长的一段（1.5GB 的周报可能传几十分钟），而这段**服务端没有任何
存在证明**。传挂了就等于什么都没发生过。

见 issue #9。

## What Changes

- **新增批次状态 `UPLOADING`**，在**签发凭证时**就落一条批次记录。object key 在签发那一刻
  就已确定（凭证策略正是限死到这个 key 上），因此记录一开始就是完整可溯源的。
- **`/oss/import` 认领已有批次而不是新建一条**。按 object key 匹配（key 含 uuid，一次上传
  一个）。认领不到时仍新建——接口不能因为记录被回收过就变得不可用。
- **`UPLOADING` 必须会被收尾**，否则它和历史上的 `QUEUED` 犯同一个病：用户关掉标签页之后
  没有任何东西回头看这条记录，界面永远显示「上传中」，比「什么都不显示」只是换了句谎话。
  收尾由既有的轮询任务承担，判据是**超时 + 对象是否真的在**：
  - 对象在 → 说明字节传完了、只是 `/oss/import` 没被调到（关标签页的典型形态）。这条不算
    失败，**直接置 `QUEUED` 交给排队接手者导入**——文件已经在 OSS 了，让用户重传一遍毫无道理。
  - 对象不在 → 判 `FAILED`，写明「上传未完成，请重新上传」。
- **超时阈值由 `OSS_STS_DURATION_SECONDS` 推导，不新增配置项**。理由见 design 决策 2。

**不做**（明确排除）：

- **不改前端、不动历史屏 UI。** 本变更只保证「记录存在且状态诚实」。呈现由导入历史屏
  （变更 `add-import-history-view`）承担，两者在 `import_batch.status` 上对接。
  在那个屏合并之前，`UPLOADING` 记录可以从 `GET /processing-status` 看到。
- **不改本地退路**（`OSS_ENABLED=false` 的 `/import-csv`）。它没有签发凭证这一步，
  文件经 HTTP 落盘，中断由 HTTP 请求本身报错，不存在「无感」问题。
- 不改三段式导入内核、不改串行锁与排队机制、不改错误契约。

## Capabilities

### Modified Capabilities

- `oss-first-ingestion`: 批次记录的生命周期从「导入触发时创建」提前到「签发凭证时创建」，
  并新增上传阶段的状态与其收尾规则。
