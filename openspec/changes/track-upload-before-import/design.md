# 设计

## 决策 1：状态加在 `import_batch.status` 上，不另起一张表

`status` 是 `String(16)`，没有 PG enum、没有 CHECK 约束，取值由应用层的 `VALID_STATUSES`
约束。因此加一个 `UPLOADING` **不需要改表结构**。

唯一要动库的是那一列的注释——它现在写着 `QUEUED（排队）/ PROCESSING / COMPLETED / FAILED`，
少了新状态就成了错的文档。列注释参与 alembic 的 autogenerate 比对，改模型注释必须配一条
迁移（见 CLAUDE.md「迁移注意」），故本变更带一条纯 `COMMENT ON` 的迁移。

不另起表的理由：上传与导入是同一件事的两个阶段，共用站点/周期/期次/文件名/object key
五个字段。拆成两张表要么两处重复这五个字段，要么让历史屏做一次 UNION，而用户在界面上
要问的问题（「我那个文件到底怎么样了」）本来就不区分阶段。

## 决策 2：超时阈值由凭证有效期推导，不新增配置项

**判据不是「多久算久」，而是「还有没有可能传完」。**

直传的每个请求都由 STS 临时凭证签名，凭证有效期是 `OSS_STS_DURATION_SECONDS`（默认 3600 秒）。
过期之后后续分片请求一律被拒，这次上传**再也不可能完成**。所以阈值取

```
凭证有效期 + 宽限 300 秒
```

宽限留给时钟偏差与「最后一个分片正在途中」。

**为什么不开一个 `UPLOAD_STALE_MINUTES`。** 它与凭证有效期是同一件事的两种说法，两个独立
旋钮迟早互相矛盾，而矛盾的两个方向都很糟：阈值短于凭证有效期，会把**正在好好传**的 1.5GB
周报判死；阈值远长于凭证有效期，用户要多等无谓的几十分钟才看到失败。推导出来的值不会
偏离，改凭证有效期时也不会有人忘了跟着改另一个。

`OSS_ENABLED=false` 时本变更整条路径不生效（本地退路没有签发凭证这一步），阈值取什么都无所谓。

## 决策 3：收尾挂在既有轮询任务上，不新起后台任务

`import_queue.run_queue_drainer` 已经在 lifespan 里按 `IMPORT_QUEUE_POLL_SECONDS` 轮询。
回收挂在同一轮里，多一次 SELECT。

**为什么不是「前端在 onerror 里回报一下」**：前端根本没机会执行 onerror 的场景——进程被杀、
断电、关标签页——恰恰就是这个变更要覆盖的场景。这与 CLAUDE.md 对 `QUEUED` 立的规矩同源：
接手要靠轮询，链式接力在最需要它的时候正好断链。

**为什么不新起一个后台任务**：多一个任务就多一处「它有没有在跑」要回答的问题，而它要做的
事（一次带条件的 SELECT + 若干 head_object）在一次轮询里是微秒到毫秒级的开销。

## 决策 4：对象还在就直接接手导入，不判失败

超时的 `UPLOADING` 批次有两种，靠一次 `head_object` 分开：

| 对象在 OSS 里 | 说明 | 处置 |
|---|---|---|
| 在 | 字节传完了，只是 `/oss/import` 没被调到（关标签页的典型形态） | 置 `QUEUED`，交排队接手者导入 |
| 不在 | 传到一半断了，OSS 里没有完整对象 | 判 `FAILED`，写明请重新上传 |

**「对象在就导入」是这个变更真正省事的地方**：文件已经躺在 OSS 里了，让用户重传一遍 1.5GB
毫无道理。而且这条路径完全复用既有机制——置 `QUEUED` 之后，接手、串行锁、失败落状态全部
由 `drain_import_queue` 承担，本变更不引入第二条导入路径。

**不做大小校验的补偿**：`/oss/import` 会在触发导入前称量对象并对超限拒绝，而这条路径绕过了
那个端点。因此回收时同样要称量——否则一个超限文件可以靠「不调 /oss/import」这条路绕过上限。

## 决策 5：`/oss/import` 认领不到批次时仍新建

按 object key 找不到 `UPLOADING` 批次的情形是真实存在的：回收任务刚把它判成 `FAILED`、
或者调用方跳过了签发直接调导入（测试与运维脚本会这么干）。

这时**新建一条**，而不是报错。理由是这个端点的契约是「凭 key 触发导入」，它不该因为
另一条链路的记账状态而变得不可用——那会把一个记账问题升级成功能不可用。

认领的匹配条件是 `object_key` 相等且状态为 `UPLOADING`。object key 含 uuid，一次上传对应
一个 key，不存在误认领。

## 决策 6：签发凭证时落库失败，就不签发凭证

签发与落库的顺序是**先落库、后签发**。落库失败（数据库不可用）时直接抛错，用户看到的是
「暂时无法上传，请稍后重试」，而不是一份能用的凭证配一条不存在的记录——后者会精确地
重建这个变更要消灭的那个状态：文件传上去了，服务端不知道。

反过来（先签发后落库）没有任何好处：凭证签发是纯计算 + 一次 STS 调用，不产生副作用，
不签它不留垃圾。

## 权衡与已知边界

- **一次上传对应一条记录，用户重试会产生多条。** 用户点两次上传就是两条 `UPLOADING`，其中
  一条终将超时被判 `FAILED`。这是对的：那确实是两次上传尝试，历史屏应当如实显示两条。
- **回收有最长一个轮询间隔的延迟**（默认 30 秒）。相对于一小时的凭证有效期可以忽略。
- **凭证有效期内断掉的上传，要等满一小时才判失败。** 可以更快——但要更快就必须知道
  「用户不再传了」，而那正是服务端不可知的事。宁可晚一小时说实话，不要早一分钟猜错，
  把正在传的大文件判死。
