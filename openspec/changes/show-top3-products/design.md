## Context

`fact_daily` / `fact_weekly` 自建模起就有 `top1/top2/top3_product_id` 与各槽位的
`click_share` / `conversion_share`，`importer._load_facts` 一直在写这三个槽位，
`_upsert_dimensions` 也把品牌#1/2/3、类目#1/2/3 按槽位落进了 `dim_product`。
断点只有一处：`analysis_crud._base_query` 只 JOIN 了 `top1_product_id`。

因此这是一个**纯读取路径**的变更：无数据库结构改动、无 Alembic 迁移、无导入链路改动。
容量约束（RDS 2C4G、应用 4C8G）依然适用，但本变更对它们的影响是可界定的（见下）。

现有的口径约定必须原样守住：份额是 0~100 的百分数、界面/接口/导出三处不做换算；
排名变化保留原始符号。

## Goals / Non-Goals

**Goals:**

- 行数据与导出覆盖点击量前三的商品，槽位与名次严格对应。
- 表格以卡牌列呈现前三，撤掉与之重复的 top1 平铺列。
- 缩略图零新增数据链路。
- 筛选与排序的 top1 口径**由结构保证**，而不是靠注释和自觉。

**Non-Goals:**

- 筛选扩到前三任一槽位命中（需要新索引，且三路 OR 在 8 亿行事实表上的执行计划不可控，
  必须先在真库上实测）。
- 类目列合并为「前三类目」。
- 自建商品图片抓取、存储或缓存。
- 任何表结构或索引变更。

## Decisions

### 决策一：新增 alias 关联，而非改写现有 JOIN

`_base_query` 保留 `DimProduct`（未 alias）承担 top1 的关联，新增两个 `aliased(DimProduct)`
承担 top2 / top3。

**为什么不把三个都改成 alias**：`_apply_filters` 里全部商品维度的筛选条件都写在 `DimProduct.xxx`
上。保持 top1 那一路不 alias，这些条件一个字都不用改，且**新增的 alias 对筛选代码不可见**——
想让筛选扩散到其他槽位，必须显式修改 `_apply_filters` 引用新的 alias。口径由此成为结构事实，
而不是一条会被后来者无意打破的约定。

**替代方案**：三路统一 alias + 在筛选处显式指定 `p1`。更"对称"，但把一处结构性保证换成了
命名自觉——写错 `p2` 就是一个静默的口径变更，测试不一定抓得到。不值得。

### 决策二：响应契约用扁平字段，不用嵌套数组

新增 `top2_asin`…`top3_conversion_share` 共 12 个平铺字段，而非 `tops: [{...}]` 数组。

**理由**：排序字段名（`top1_click_share`）已经在扁平命名空间里，且排序白名单本变更不动；
payload 改成嵌套会造成「排序键」与「数据键」两套命名并存。导出是 `(字段名, 中文表头)` 列表
驱动的，扁平字段直接加对儿即可，嵌套则需要额外一层拍平逻辑。渲染需要的数组形态由前端一个
纯函数就地拼出，可直接单测，成本远低于契约分裂的代价。

### 决策三：缩略图热链，地址推导集中一处且不按站点分支

`productImageUrl(asin)` 纯函数，返回 `https://m.media-amazon.com/images/P/<ASIN>.01._SL112_.jpg`。
组件只调函数。

**为什么不落库**：报表不含图片地址，落库意味着新增抓取链路、缓存与失效策略——为一个辅助
识别信息引入一整条数据链路，不成比例。

**为什么不按站点分支**（实测修正，2026-08-04）：原计划按站点映射图床域名与市场码。实测
推翻了这个前提——`.01.` / `.02.` / `.03.` 与 `images-na` / `images-eu` 的任意组合，对同一
ASIN 返回**完全相同**的字节，连只在德国站销售的商品（ASIN 即 ISBN）也一样。图床按 ASIN
全局解析，该段取值被忽略。保留映射不会带来任何好处，却会带来一个真实的坏处：站点清单增长
时未登记的站点直接不出图。

**但那一段不能省略**：少了它，`_SL112_` 不再被当作尺寸指令，返回全尺寸原图——实测
12.7KB vs 1.5KB。一页 50 行 × 3 张图是 1.8MB 与 225KB 的差别。故固定写 `.01.`。

### 决策六：降级判定靠图片尺寸，不能只靠加载错误事件

**实测发现**（2026-08-04）：图床对不存在的 ASIN 返回的是 **HTTP 200 + 43 字节的 1×1 透明
GIF**，不是 404。这意味着 `<img onError>` 永远不会触发，原计划的降级机制在最常见的失败
情形下**完全失效**，用户看到的是一个被拉伸的空白方块——比占位符更糟，因为它看起来像
"图还在加载"。

因此降级判定改为：`onLoad` 时检查 `naturalWidth/naturalHeight`，1×1 即判定为无图；
`onError` 保留，负责真正的网络失败。两者共用同一个降级状态。

这类失败无法靠 code review 或类型系统发现——它只在真实图床的真实响应下暴露，这也是把
"用真实 ASIN 实测"单列为一条不可跳过任务的价值所在。

### 决策四：导出扩列而非另开导出端点

`_EXPORT_COLUMNS_BASE` 直接扩展。导出复用 `_base_query`，字段自动跟随。

**对内存与连接的影响**：行数不变、`yield_per` 分块大小不变，故驻留内存与块大小同阶这一性质
不变；单行变宽约一倍（约 24 列 vs 12 列），块内驻留内存随之约翻倍，但基数是 2000 行 × 一行
几百字节的量级，在 8 GiB 应用服务器上无实质影响。`EXPORT_ROW_CAP` 与"上限判定必须在开流前
完成"两条约束均不受影响。连接占用不变——仍是一次导出一个同步会话。

### 决策五：口径差异标注在过滤区，不标在表格

「筛选只作用于第一名」的提示挂在过滤区的品牌、类目、商品标题、份额条件旁，而不是表格列头。

**理由**：误用发生在用户"拿看到的值去填筛选"的那一刻，提示要出现在填写的位置才拦得住。
标在表格列头则是在用户产生意图之前提醒，读的时候没有上下文，填的时候已经离开视野。

## Risks / Trade-offs

- ~~图床市场码约定不确定（GB / DE 尤甚）~~ → **已实测排除**：市场码与图床域名均不影响返回
  内容，映射已删除（见决策三）。实测同时暴露了一个更严重的问题——占位像素不触发 `onError`
  （见决策六），若未实测将带着一个失效的降级机制上线。
- **无图的 ASIN 会显示占位方块，且无法预先知道哪些有图** → 图床不提供"是否有图"的查询，
  只能加载后判定。合成/测试数据下几乎全是占位方块，真实数据下比例未知；这不影响任何信息的
  可读性（ASIN 与两个份额都是文本渲染）。
- **国内访问亚马逊图床的速度不受我们控制** → 已用延迟加载限制并发请求；图片失败不阻塞任何
  信息展示（ASIN 与两个份额都是文本渲染）。若实测速度不可接受，回退方案是关掉图片位、保留
  卡牌其余部分——布局不需要重做。
- **两个额外 LEFT JOIN 的查询代价** → 按 `dim_product` 主键关联，每页 20 行即两次主键嵌套循环，
  相对现有的事实表分区扫描可忽略。事实表的索引使用不受影响：新 alias 只出现在 SELECT 与 JOIN
  条件中，不进入 WHERE，故不改变现有执行计划的选择。**导出路径需留意**：一次导出可达
  `EXPORT_ROW_CAP`（默认 5 万）行，两个额外的主键探查随行数线性增长，实测时应对比扩列前后的
  导出耗时。
- **行高从一行文本涨到约 90px** → 单屏可见行数减少约一半。这是卡牌式呈现的必然代价，用户已
  确认接受。
- **前端契约扩了 12 个字段** → `AnalysisRow` 与后端 schema 必须同步扩；两处不同步的表现是
  `undefined` 静默渲染成空卡牌。由前端列渲染的单测覆盖空值路径来兜。

## Migration Plan

无数据库迁移——字段已存在于 `analysis` schema 下的两张事实表中，本变更不涉及任何 DDL。

部署即常规发布：后端随 `./deploy.sh` 更新，前端 SPA 重新构建发布。回滚为代码回滚，
无数据侧动作、无需回填。前后端可分别回滚：后端多返回的字段被旧前端忽略，新前端遇到
缺字段的旧后端则渲染为空卡牌（不崩），故发布顺序不构成硬约束——但建议先后端后前端，
让新字段先就位。
