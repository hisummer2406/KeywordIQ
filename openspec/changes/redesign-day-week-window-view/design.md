## Context

现状：分析屏的作用域是「站点 + 视图 + 日期」三元组，任一查询只落在**单一事实切片**上。这条约束是 `site-scoped-query` 的核心，也是当前性能表现的来源——每次查询的扫描范围由一期数据的大小决定，与保留窗口的长度无关。

本变更要打破的正是这条约束的时间那一维：行集合从「锚定期这一片」放宽为「行窗口内出现过的关键词」。站点那一维不动。

三个既有约束框住了实现空间：

- **硬件**：应用 4 vCPU / 8 GiB，RDS PostgreSQL 2C4G。库上同时真正能执行的查询约 4 个，池开大不提升吞吐。
- **体量**：日报约 30 万行/站/期，周报约 300 万行/站/期。天视图的 7 天行窗口覆盖约 210 万行，周视图的 4 周行窗口覆盖约 1200 万行。
- **既有哲学**：事实数据写入时算定派生值、只追加不回改；查询层不算派生值、不持状态。排名变化、上期排名、是否新词都是这么来的。

本变更建立在 `async-query-path`（28/32 已勾）之上——查询层已是 `async def` + `AsyncSession`，导入仍是同步。

## Goals / Non-Goals

**Goals:**

- 让「刚刚掉出榜单」这个信号在界面上可见，而不是靠人肉对比两天的导出文件。
- 提供三个历史参照点（上期 / 4 期前 / 12 期前），把「短期波动」与「趋势性下滑」区分开。
- 新增的运行成本落在**导入侧每期一次**，而不是查询侧每次翻页——查询路径的性能特征保持与现在同阶。
- 天视图与周视图同构：同一套代码，只有窗口长度与参照点偏移量不同。

**Non-Goals:**

- **不做月视图**。导入链路只认 `DAY` / `WEEK`，没有月度数据源。
- **不做搜索量、展示量/点击量、PPC 竞价、SPR、标题密度**。ABA 报表的 21 列里没有这些字段，需要另一条数据源与导入链路，单独立变更。
- 不改导入三段式主干、OSS 链路、错误契约、权限模型。
- 不回填历史分区的掉榜记录。
- 不为掉榜行做跨期的属性合并（品牌/类目/份额一律不从最后在榜期顶替到当期列）。

## Decisions

### 决策 1：掉榜集合在导入时算定并持久化，而非查询时实时计算

**选定**：新增 `analysis.fact_dropped`，导入收尾时算出该期的掉榜集合写入。

**替代方案 A：查询时实时算**（`窗口内出现过 EXCEPT 当期出现`）。天视图要在 180 万行上做反连接、周视图 900 万行，且**每翻一页重跑一次**。翻十页就是十次。否决。

**替代方案 B：实时算 + 应用层缓存集合**。省掉表和迁移，但引入缓存失效、内存占用、首次查询仍然慢三个新问题，还破坏了「查询层不持状态」——多 worker 下每个 worker 各存一份，8 GiB 内存下不可控。否决。

选定方案与既有哲学一致：掉榜是**锚定期的一项事实**，锚定期一旦确定就不再变化，正好落在「写入时算定、只追加」的模式里。成本从「每次查询」降到「每期一次」。

### 决策 2：`fact_dropped` 只做单级月度分区，不做站点二级分区

事实表是 `RANGE(report_date)` → `LIST(site)` 两级。掉榜表**只做一级月度 RANGE**，站点作为普通索引列。

理由：掉榜集合是差集而非全量，体量比事实表小一到两个数量级（日报的日间流动量级预计在几万到十几万）。二级分区的收益是分区裁剪，而这个量级下索引裁剪已经够用；代价是分区数翻倍（站点数 × 月数），增加计划时间与 DDL 维护面。

保留清理照常工作——按月 `DROP` 一级分区即可，与事实表同一套逻辑。

```
analysis.fact_dropped
  site            varchar(8)   ┐
  period_type     varchar(8)   ├ PK
  anchor_date     date         ┤   ← 分区键（PostgreSQL 要求 PK 含分区键）
  keyword_id      bigint       ┘
  last_seen_date  date  NOT NULL
  last_ranking    int   NOT NULL
  created_at      timestamptz  DEFAULT now()
PARTITION BY RANGE (anchor_date)   -- 月度

索引：
  PK (site, period_type, anchor_date, keyword_id)              -- 存在性判定与去重
  (site, period_type, anchor_date, last_ranking)               -- 掉榜段的排序与分页
```

### 决策 3：历史排名不单独查，从趋势回溯结果里取

看似要为三个参照点各做一次查询，实际不必——**参照点全部落在趋势回溯范围内或只差一期**：

| 视图 | 趋势渲染 | 参照点 | 回溯查询实际取的范围 |
|---|---|---|---|
| 天 | `[d-6, d]` 7 点 | `d-1` / `d-3` / `d-7` | `[d-7, d]` 8 期 |
| 周 | `[w-3, w]` 4 点 | `w-1` / `w-4` / `w-12` | `[w-11, w]` 12 期 |

两个视图都是「回溯范围 ≥ 趋势窗口」：天多取一天（`d-7`），周多取八周（`w-11`）。多取的那部分只喂历史排名列，不进趋势小图，也不影响行集合。

于是历史排名列**不新增任何查询**，只是对已经拿到的回溯结果做取值。

**趋势窗口不跟着参照点走**：周视图的行窗口是 4 周，小图就画 4 点。配一条 12 周的线会让人无从判断线上哪一段对应表里这批行——参照点要的是「某一期的那个数」，小图要的是「这段时间的形状」，两者不必同宽。

**替代方案**：新增 `history_stmt` 单独查三个日期。多一次往返、多一段要维护的 SQL，换来的只是趋势与历史排名解耦——而这两者本来就该对齐。否决。

### 决策 4：排名变化率不进接口，由前端从已有字段算

变化率 = 排名变化 ÷ 上期排名，两个字段都已在响应里。多下发一份的唯一后果是两处口径漂移时产生互相矛盾的数字，而这类漂移在改动其中一处时不会有任何测试报错。

### 决策 5：分段分页——在榜段与掉榜段串联，边界由预存计数划定

两段各自有序（在榜按用户选定的排序字段，掉榜按最后在榜排名），且**永不交错**——掉榜恒在末尾。因此分页可以在应用层按边界切分，不需要 `UNION ALL` + 外层排序（那会强制物化两段全部行）：

```
listed_total  = 无筛选 ? site_data_stats.row_count : count_filtered(锚定期切片)
dropped_total = 无筛选 ? site_data_stats.dropped_count : 0
total         = listed_total + dropped_total

include=LISTED   → 只查在榜段
include=DROPPED  → 只查掉榜段，offset 原样
include=ALL      → offset + size <= listed_total  : 只查在榜段
                   offset >= listed_total          : 只查掉榜段，offset -= listed_total
                   否则（跨界）                     : 在榜取 [offset, listed_total)
                                                     掉榜取 [0, size - (listed_total - offset))
```

**带筛选时 `dropped_total` 恒为 0**，掉榜段直接短路——这就是「筛选以锚定期为准」这个选择的兑现方式，也让带筛选的查询路径与现在一字不差。

这一段是全场最容易写错的地方，四种边界（整页在前段 / 正好跨在分界线 / 整页在后段 / 两段各出一半）必须各有一个集成测试。

### 决策 6：掉榜行的当期字段留空，不用最后在榜期的值顶替

掉榜行的商品槽位、品牌、类目、份额全部为空。顶替会让同一列混入不同期次的数据，用户无法判断某一格属于哪一天——而整张表的可读性正建立在「一行属于一个期次」上。掉榜行携带的跨期信息只有明确标注了期次的那两个字段（最后在榜期、最后在榜排名）。

## 数据库迁移

两条手写迁移（分区表不在 SQLAlchemy 的 DDL 生成范围内，autogenerate 会把它产成普通表并静默丢掉分区）：

1. **建 `analysis.fact_dropped`**：`CREATE TABLE ... PARTITION BY RANGE (anchor_date)`，建父表索引（PostgreSQL 自动传播到子分区），并创建当前月及前两月的初始分区。
2. **`analysis.site_data_stats` 加 `dropped_count`**：`ADD COLUMN bigint NOT NULL DEFAULT 0`。该表按 (站点,周期,期次) 一行，行数是三位数量级，带默认值的加列在这个体量下无碍。

两条迁移都显式限定 `analysis` schema。落库前用 `alembic upgrade head --sql` 核对生成的 DDL 里确有 `PARTITION BY`——这是这个仓库踩过的坑。

`partitioning.ensure_fact_partitions` 需扩展为一并确保掉榜表的月度分区存在（写入前无条件调用，幂等）。`retention_service` 需把掉榜表纳入按月 `DROP` 的清单。

downgrade：`DROP TABLE analysis.fact_dropped` / `DROP COLUMN dropped_count`。掉榜记录是可重算的派生数据，回滚不丢原始事实。

## 连接池、内存与执行计划

**连接池**：不新增连接。掉榜集合的计算跑在导入既有的同步会话与事务里；查询侧的掉榜段查询与在榜段在同一个 `AsyncSession` 内串行，异步池占用不变。`async-query-path` 定的池配置不受影响。

**内存**：掉榜集合的计算是纯库内 `INSERT ... SELECT`，**不把任何行读进应用进程**。库内排序受 `work_mem` 限制，超出即外部排序落盘，内存有界。这与「导入靠 COPY 流式装载保持内存有界」的约束一致。

查询侧每页仍是 20 行量级；趋势回溯的范围从 7 期扩到 8 期（天）/ 12 期（周），是每页 20 个关键词的回溯，量级不变。

**执行计划**：

- 掉榜集合计算：`DISTINCT ON (keyword_id)` + `NOT EXISTS` 反连接。窗口内各期分区的 PK 是 `(site, report_date, keyword_id)`，对给定的 `(site, report_date)` 天然产出 `keyword_id` 有序，计划器可用 MergeAppend 跨分区归并，避免对 180 万（天）/ 900 万（周）行做全量排序。**这是推断，必须实测确认。**
- 掉榜段查询：走 `(site, period_type, anchor_date, last_ranking)` 索引，索引顺序即分页顺序，无排序节点。
- 在榜段查询：一字不改，沿用现有计划。
- 事实表**不加列**，因此没有表重写、没有已有索引失效。

## Risks / Trade-offs

**[周视图掉榜集合的计算耗时未知]** → 900 万行反连接，我的估计是十几到几十秒，但这是推断不是实测。周报导入本身是 GB 级 `COPY`，多这一步大概率可接受，但**必须在真实体量上实测并把数字回填本文档**。若超出可接受范围，回退方案是把周视图行窗口从 4 周降到 2 周（规格里窗口长度是可配置的口径，不是硬编码语义）。

**[分段分页依赖预存计数的准确性]** → 预存的 `row_count` / `dropped_count` 与实际行数不一致时，跨界页会重复或漏行，而这种错误在界面上表现为「某一行出现两次」，极难归因。缓解：计数写入与事实/掉榜写入在同一事务内提交；四种分页边界各有集成测试；`include=DROPPED` 路径不依赖 `listed_total`，可作为交叉验证的手段。

**[历史分区没有掉榜记录]** → 本能力上线前导入的日期切到「全部」时只有在榜行，与上线后的日期表现不一致。缓解：不报错、不为空表；数据只留三个月，自然滚动约两周（日报）/ 一个月（周报）后全部覆盖。不做回填——回填要为每个历史期跑一次全量反连接，代价与收益不成比例。

**[「筛选一加，掉榜行全没」是反直觉的]** → 这是「筛选以锚定期为准」的必然后果，且是用户明确选定的口径。缓解在界面侧：筛选生效时明示本次结果不含掉榜行；「仅掉榜」时其余筛选置灰。若不做这两处提示，用户会把它当成系统弄丢了数据。

**[打破了「单一事实切片」这条写在 CLAUDE.md 里的约束]** → 该约束是当前性能表现的理论依据，放宽后需要新的表述。缓解：约束改写为「单一站点 + 锚定期 + 行窗口」，并明确带筛选路径仍锁死在单一切片；CLAUDE.md 的「V2 查询层」一节随本变更同步修改，不留一份与代码矛盾的文档。

**[与在飞变更的时序]** → `async-query-path`（28/32）改的是同一批文件的执行模型。本变更须在其合入之后开工，否则两边都要改 `analysis_crud` / `analysis_service` 的同一批函数。开工前确认其剩余 4 项已完成。

## 实测（2026-08-06，天视图）

US 站真实日报三期（`2026-05-03` / `05-04` / `05-06`，每份 240–270 MB CSV），本机
PostgreSQL 15，脚本 `scripts/measure_dropped.py`：

| 锚定期 | 在榜行 | 窗口内前置期 | 掉榜行 | 占在榜 | 掉榜算定 | 整期导入 | 占比 |
|---|---|---|---|---|---|---|---|
| 05-03 | 471,584 | 0 | 0 | — | 0.04s | 150s | — |
| 05-04 | 426,516 | 1 | 88,356 | 20.7% | **1.24s** | 105s | 1.2% |
| 05-06 | 425,304 | 2 | 120,223 | 28.3% | **1.74s** | 101s | 1.7% |

`fact_dropped` 两期共 20.9 万行，含索引 **23 MB**。

三点结论：

1. **决策 1（导入时算定）的代价可以忽略。** 掉榜算定占整期导入的 1–2%，而它换掉的是
   查询侧每翻一页一次的反连接。
2. **实际日报体量比 CLAUDE.md 记的大。** 文档写「~30 万行 / ~150 MB」，实测是
   **42–47 万行 / 240–270 MB**。凡按 30 万行推导的估算都要按 1.5 倍重算——本文档前面
   「天视图行窗口约 210 万行」的说法，真实值是约 **280 万行**。
3. **掉榜段不是一个小尾巴。** 只有 1–2 个前置期时就已占在榜行的 20–28%；生产的完整
   窗口有 6 个前置期，占比只会更高。这有两个后果：**决策 5 的分段分页必须写对**
   （掉榜段大到用户翻得进去，不是理论边界）；存储上按 6 期窗口外推，天视图约
   20 万行/期 × 90 期 ≈ 1800 万行/站、约 2 GB/站，与事实表相比仍是小头，但不可忽略。

**测量的两处局限**（不要把上表当作生产值）：

- **窗口深度不足。** 手上只有三份可凑窗口的日报，最深只有 2 个前置期，生产是 6 个。
  扫描量与掉榜行数都会更大，`1.74s` 是**下界**而非典型值。
- **本机不是 RDS。** 生产是 2 vCPU 的 RDS，比本机慢。
