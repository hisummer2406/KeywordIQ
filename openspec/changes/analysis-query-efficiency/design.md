## Context

第一阶段（`archive/2026-10-24-post-import-query-readiness`）已交付：新期次可见前 `ANALYZE`、语句超时 30 s、完整请求预算 25 s（`_bound_statement_to_deadline`，每条语句 `SET LOCAL statement_timeout`）、每 worker 4 个并发位与 5 s 有界排队（`search_slot`）。性能预算见该变更 design「性能预算」：日报 p95 ≤ 3 s、周报 p95 ≤ 5 s、单请求 25 s。

约束事实：

- 经 SQLAlchemy 的 asyncpg 适配层取消协程，服务端语句不会停。任何「取消」需求都必须让数据库侧真正停止（#148 实测）。
- 前端 `useAnalysisQuery` 已用 `requestSeqRef` 丢弃过期响应，但不中止请求（见该文件注释：`useFetchData` 的 `abortFetch` 只掐断内部等待）。
- 并发闸与去重都是进程内状态；生产 4 个 worker，无跨进程协调组件。

## Goals / Non-Goals

**Goals：** 减少重复工作；过期/断开请求不再白占数据库；慢筛选达到预算；拥堵时轻量接口不退化；缓存（若启用）绝对正确。

**Non-Goals：** 跨 worker 的全局去重或全局并发上限；引入 Redis 等新组件；增加连接数/升级硬件；改动导入、导出口径；任何生产操作。

## Decisions

### D0 先重采、再定深度（闸门）

本变更的「优化前」基线是发布 #149 后的生产重采（#148 tasks 7.5），日报、周报分开统计；重采需要请求摘要能区分视图（D6）。D1、D2、D6 与前端中止不依赖基线，可先做；D3（品牌词/计数）与 D4（缓存默认开启与否）的深度以重采为准：日报、周报在预算内且 `stage_ms` 无明显主导阶段则不做 D3 的结构性改动，只保留测量。

### D1 请求去重（单飞）

进程内 single-flight：键为 `(user_id, 规范化请求体哈希, 数据版本)`。规范化包括筛选、分页、排序、作用域（site/view/on）；忽略无语义差别的字段顺序。第一个请求创建执行任务，后续同键请求等待同一结果。

- 键含 `user_id`：`competitor_new` 与权限范围都由用户决定，不同用户不合并是最简单的无泄露保证。
- 合并发生在并发闸**之前**：等待者不占并发位，也不占连接。
- 执行任务用引用计数：所有等待者离开才取消底层任务（见 D2）。
- 仅同 worker；跨 worker 的重复不合并，属已接受的局限，上限即 worker 数。
- 数据版本取自 `site_data_stats` 中该 `(site, period, report_date)` 的版本戳（导入完成/重导/统计刷新会变化），读取为一次轻量主键查询。

### D2 取消传播

分两段：

1. **前端**：`searchAnalysis` 接受 `AbortSignal`；`useAnalysisQuery` 在发起新请求前中止上一个。被中止的请求不触发错误态；保留 `requestSeqRef` 作为二次保护。
2. **后端**：请求处理在独立任务中执行，同时监听 `request.is_disconnected()`；断开或 `CancelledError` 时由**独立的辅助连接**对该请求的后端进程发 `pg_cancel_backend(pid)`。

不误取消他人的防护：

- 请求在每次借到连接后记录 `pg_backend_pid()` 与一个请求级令牌，令牌写入 `SET LOCAL application_name`（事务内）；取消前先在辅助连接核对 `pg_stat_activity` 中该 pid 的 `application_name` 仍等于该令牌且 `state='active'`，才发取消。连接已归还并被他人借用时令牌不匹配，不会取消。
- 取消只作用于单个 pid，不用 `pg_terminate_backend`，不影响连接复用。
- 辅助连接走独立的小池（1 条，有上限），不占业务异步池，取消本身受短超时约束。

此机制先做**机制验证**（tasks 3.1）：在真库验证取消后 `pg_stat_activity` 无残留、连接可复用、他人语句不受影响，再接入请求路径。若令牌核对在实测中不可靠，退回到「仅依赖 D3 的按截止时间由数据库取消」，并在 design 记录。

### D3 品牌词排除与计数优化（待基线）

先加测量，不先改：`stage_ms` 已有 count/rows/trend 阶段；补充视图维度（D6）。重采后若日报或周报超预算，按主导阶段选择：

- 候选 A：品牌词排除改为以首次入榜集合为驱动的反连接，避免对大 `dim_keyword` 做逐行判断。
- 候选 B：精确计数与取行共享同一过滤中间结果，避免重复扫描。
- 候选 C：导入时预聚合（与「聚合挪到导入时」的产品方向一致）。

约束不变：精确总数、分页边界、黑名单、首次入榜、掉榜、列表与导出一致；不截断计数、不删筛选。任何改写都要有等价性回归（同一条件改写前后行集合与总数一致）。具体选择在重采后补充到本节。

### D4 结果缓存（可选，默认关）

进程内 LRU+TTL：键同 D1 且包含数据版本；`competitor_new` 为真的请求不缓存（依赖用户私有关注数据，且关注变更没有数据版本）。配置：`ANALYSIS_RESULT_CACHE_ENABLED`（默认关）、`ANALYSIS_RESULT_CACHE_MAX_ENTRIES`、`ANALYSIS_RESULT_CACHE_TTL_SECONDS`，同步 `.env.example` 的单位与安全默认值。

- 失效靠键里的数据版本，不靠主动清理：重导、统计刷新、保留清理都会改变版本戳，旧条目自然不再命中并被 LRU 淘汰。
- 默认关：是否开启由重采后的收益门槛决定（命中率、对 p95 的改善）；机制与测试先落地。
- 缓存的是序列化前的响应模型，命中时不重新执行任何数据库语句，但鉴权与权限检查仍先执行。

备选：Redis/跨进程缓存。否决：新组件与运维面，对 4 个 worker 的规模不值得。

### D5 拥堵时保护轻量功能

先测量再动：在分析查询并发满载下，压测 `/api/auth/me`、`/api/analysis/scope` 的延迟。第一阶段已让排队者不占连接，故预期已达标；若不达标，候选是为轻量请求保留连接（拆出独立的小池）或调低分析并发位，而不是整体加大池。并发闸按 worker 计（合计 16），是否足够以重采的并发形态和压测为准；任何容量调整保持既有全局连接上限算式。

### D6 诊断

- 请求摘要与慢查询诊断带 `view`（DAY/WEEK），使重采能分日周统计（#148 tasks 7.4 的前置）。
- 排队超时、语句/请求超时、统计 `PENDING/FAILED` 的提示按 `(类型, site, view)` 在时间窗（默认 60 s）内去重，窗口内只记首条并累计次数，总量有界。
- 不新增对用户的弹窗；用户侧文案沿用既有 503 文案。

## Risks / Trade-offs

- [取消误伤] pid 复用风险由令牌核对 + 单 pid 取消控制；机制验证不过则不接入。
- [单飞放大延迟] 一个慢请求让多个等待者一起等；它们本来各自也要等同样久，且等待者不占并发位，净收益为正。
- [缓存一致性] 默认关闭 + 数据版本键 + 私有结果不缓存；一致性回归必须通过才允许默认开启。
- [仅同 worker] 4 个 worker 下最坏仍重复 4 次，接受。
- [闸门式交付] 变更会跨越发布与重采，tasks 的 D3/D4 项明确标为阻塞项，不预先实现。

## Migration Plan

无数据迁移。新配置默认保持现有行为（缓存关）。单飞与取消无开关则风险偏高，两者各设一个关闭开关（`ANALYSIS_SINGLEFLIGHT_ENABLED`、`ANALYSIS_CANCEL_ON_DISCONNECT_ENABLED`，默认开），便于线上出问题时回退。
