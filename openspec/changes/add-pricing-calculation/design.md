## Context

- 现状：前端 `frontend/src/pages/Pricing/index.tsx` 是占位页，只有超管能看到（`canViewUnreleased`）。后端没有核价代码。业务草案见 `docs/pricing/01-product-prd.md`，原始依据见 `docs/售价计算表--26.8.17(1).xlsx`。
- 用户已确认的范围（2026-11-10）：FBA 和自发货都要做；市场分析数据是 FBA 口径，但系统也给自发货团队使用。首批市场为 US、GB、DE，以后会扩展。第一阶段直接把 PRD 的功能做齐。
- 用户不负责跨境电商的业务口径，PRD §10 的待确认项由本设计按行业惯例给出默认结论（决策 3～7）。这些结论都落在**可配置的数据**里，以后发现口径不对，改费用配置即可，不用改代码。
- 外部事实（2026-11 检索，以官方费率卡为准）：US FBA 配送费 2026-01-15 起按价格段分三档（<$10、$10–50、>$50）；2026-04-17 起 US 加收 3.5% 燃油物流附加，UK、DE 加收 1.5%；10-15 到次年 01-14 有旺季费；UK 不属于泛欧计划。费率一年调整多次，所以必须做成带生效日期的版本数据。
- 本变更不涉及日报和周报路径，不访问 ABA 事实表、分区、物化视图和导入咨询锁。

## Goals / Non-Goals

**Goals:**
- 用一个正算模型同时覆盖 FBA 和自发货，三种反推加保本价都由这个模型求解并复核。
- 费用规则数据驱动、有版本、有来源、能启停。新增市场或调整费率不需要改代码。
- 核价结果可以复现：快照记录输入、实际采用的规则版本和参数值、模型版本。
- 缺失、不适用、无解、计算失败分别给出状态，不用 0 补齐。
- 工作台三个页签：快速核价、核价记录、费用配置。另有导出、复制、重新核价、选定方案。

**Non-Goals:**
- 不接 Amazon SP-API 或 Product Fees API 实时拉取费用，不接物流报价接口，不自动拉汇率（数据结构为以后接入留了位置）。
- 不做批量 SKU 核价、真实订单利润校准（属于 #171 第二阶段），不做自动改价或上架。
- 不计算企业固定费用和所得税，结果称「预计单件利润」，不称净利润。
- 不模拟低库存费、超龄库存附加费、移除和弃置费这类与经营状况有关的费用。它们会作为「未纳入费用」列在结果旁边。

## Decisions

### 决策 1：一个正算模型，反推按分段线性求解

利润是售价 P 的分段线性函数。分段点来自类目佣金阶梯、FBA 价格段、最低佣金等。引擎先在输入和规则确定后列出所有分段点，在每一段内把利润写成 `a·P + b`，解出满足目标的 P，只保留落在本段内的解，取最小值。得到的价格按市场最小货币单位向上取整，再代回正算复核；复核不达标就再加一个最小单位，最多重复有限次，仍不达标则报计算错误。采购价上限的求法相同：利润对采购成本 C 是线性的（关税计税基础可能含 C，所以系数为 `1 + 关税率…`）。解出后向下取到分，再复核。

- 备选：二分查找。实现简单，但精度和边界依赖迭代次数，分段跳变时可能落在不可行区间，不选。
- 备选：分别推导三套闭式公式。原 Excel 就是这么做的，结果正算和反推对不上（PRD §2 的云途普货案例），不选。

### 决策 2：十进制定点与舍入

引擎只用 `decimal.Decimal`，上下文精度 28 位，禁止混入 float，在入参边界把字符串或数字转成 Decimal。中间值不截断。单项收费按规则声明的方式舍入（Amazon 费用按市场币种舍到分，物流费按人民币舍到分）。最终售价按市场最小单位处理（USD、GBP、EUR 都是 0.01），利润展示到人民币分，利润率保留两位小数。是否达标用未格式化的计算值判断。

### 决策 3：售价含税口径按市场配置（回答 PRD「乘 1.2 的含义」）

原表的「×1.2」是在不含税价上加英国和欧洲 20% 增值税，但德国标准税率是 19%，所以原表德国价格偏高约 0.8%。行业惯例和平台规则：

- **US**：前台标价不含销售税，销售税由平台代收代缴（marketplace facilitator），不进卖家收入。`price_includes_vat=false`。
- **GB / DE**：前台标价含 VAT。卖家实收要扣掉 `P × r/(1+r)`。GB 的 r=20%，DE 的 r=19%。低货值直邮由平台代扣，卖家自己申报时按销项缴纳，两种情况对单件利润的影响相同，所以统一处理。
- **佣金计费基础**是买家实付的含税总价（Amazon 欧洲站规则），不是不含税价。
- **利润率分母**是不含增值税的销售收入折人民币。另外展示「投资回报率 = 利润 ÷（采购＋包装人工＋头程＋关税）」，这是卖家常用的另一个口径。

以上都是市场参数的字段，不在代码里按国家分支。

### 决策 4：佣金与预留分开（回答 PRD「20%/17% 与 0.85」）

原表定价时用 20% 或 17%，算利润时固定乘 0.85。这说明 15% 是平台佣金（大多数类目的标准费率），另外的 2～5 个百分点是运营留给广告、退货的余量。本设计把它们拆成：

- **类目佣金**：按市场、类目配置，支持「整价适用一个费率」的阶梯（如服装按售价分段）、「超出部分适用另一费率」的阶梯（如珠宝）和最低佣金。
- **广告预留 %、退货损耗 %、结汇手续费 %**：作为核价场景的输入，计费基础都是含税售价。市场参数里提供默认值，可以在核价时覆盖，覆盖值写入快照。
- **英国数字服务税附加**：UK 对 Amazon 收取的佣金和 FBA 费用加收 2%，用市场参数 `amazon_fee_surcharge_rate` 表达。DE 为 0。

### 决策 5：关税与进口增值税（回答 PRD「不包税渠道」）

- **关税税率**由核价输入填写，**不提供默认值**。税率由 HS 编码和原产地决定，而且美国对华关税近两年变动频繁、叠加项多，用默认值等于编造。未填写时，需要关税的方案状态为「待补资料」。明确填 0 视为已确认免税。
- **计税基础**是申报价值。可以选「按采购成本」，也可以填固定金额加币种。
- **FBA**：关税 = 申报价值 × 关税率。GB、DE 的进口增值税对已注册 VAT 的卖家可以抵扣，市场参数 `import_vat_recoverable` 默认为 true；为 false 时，进口增值税（申报价值＋关税）× r 计入成本。
- **自发货渠道**有 `duty_mode` 字段：`included`（包税，承运商报价已含）或 `buyer_or_seller_pays`（不包税，按上式计算）。美国小额豁免（de minimis）2025-08 起已暂停，直邮美国同样要计关税。原 Excel 中 CNE「按申报价值 25% 收取」这类说明需要人工改写成结构化字段，不从备注推断。

### 决策 6：FBA 费用模型

一个 FBA 费率版本按市场划分，包含以下内容：

- **尺寸分段表**：按顺序排列的分段，每段有最长边、次长边、最短边、长度加周长、单件重量上限。另有体积重除数（US 为 139 in³/lb，EU 为 5000 cm³/kg）和发货重量的取法（大件取实重与体积重的较大值，信封或小件只看实重，按分段配置）。
- **配送费表**：按「分段 × 发货重量区间 × 价格段」给出金额，最高区间以上按每增加一定重量加收的方式计费。燃油附加比例、旺季费（带日期区间）作为同一版本内的附加项。
- **仓储费**：按分段和季节（1–9 月、10–12 月）给出每立方英尺或立方米的月费。核价输入填「预计平均在仓月数」，默认值来自市场参数。
- **入库配置费**：按分段给出所选配置方式的单件费用，默认用「Amazon 优化拆分」（0 费用），可以改选。
- **头程**：按市场配置共享默认值（空运或海运，每计费 kg 或每 m³ 的人民币单价，体积重除数 6000），核价时可以覆盖。

实现补充：尺寸段增加可选的「体积重上限」（EU 小号包裹 ≤ 2.10 kg、标准包裹 ≤ 7.96 kg 等同时限定体积重）。EU 旺季费在官方费率卡中是整张替换的费率表，不是在原价上加一笔，因此用规则的生效期表达：非旺季、旺季（10-15 至次年 01-14）、旺季后各一个版本，`peak_fees` 只留给「附加一笔」的情况。

尺寸或重量超出已配置分段时，结果为「不适用：超出已配置尺寸段」，并允许用户手填 FBA 配送费，来源标为「人工填写」。这是一个实际可用的兜底：用户可以从卖家后台的收入计算器抄数值，避免引擎因覆盖不到大件而无法使用。

### 决策 7：自发货渠道模型（回答 PRD「+24 元」和渠道冲突）

渠道规则包含：
- 市场、渠道名称、承运商、渠道代码，状态为草稿、启用或停用（停用需写原因）。
- 适用条件：允许的货物属性集合（普货、带电、纯电、液体、膏体、粉末、化妆品、磁性），单件最大重量，最长边，三边和，液体或膏体单瓶容量上限，以及容量的计量对象（单瓶或整单）。
- 计费：一组重量区间，每个区间有「挂号费（每票固定费）＋每 kg 单价」；起重（最低计费重量）；进位粒度（如每 0.001 kg 或每 0.5 kg 向上进位）；可选体积重除数，不填则按实重计费；附加费列表，每项有名称、金额或比例和适用条件。
- 时效天数（可选，仅用于展示，不参与推荐排序）和关税方式（决策 5）。

原 Excel 的「+24」**不是挂号费**：它只出现在德国、法国、意大利、西班牙等欧盟线路的公式里（如 `22+55*F4+24`），而同一公式里已经有挂号费（22），英国和美国线路都没有。导入脚本把它单列为「原表固定附加 24 元（欧盟线路，性质待核实）」这一项附加费，并标注来源单元格，名称和是否重复计费由维护人员核实（实现时读了原表才发现，修正了提案阶段的判断）。同一渠道的编号或容量限制前后不一致时，导入脚本把相关规则保持为草稿，并在 `review_note` 中写明冲突，不自动合并。

### 决策 8：规则存储用一张版本表，载荷用 JSONB 加 Pydantic 判别联合

规则共五类（`fx_rate`、`market_params`、`referral_schedule`、`fba_rate_card`、`fbm_channel`），每类的形状差别很大，而且官方费率卡年年调整。存储方式：

- `pricing_rule`：`id`、`kind`、`scope_key`（如 `US`、`US:CNY`、`US:<渠道码>`）、`version`、`status`（draft、active、retired）、`effective_from`、`effective_to`、`source`（必填，填 URL 或文件位置）、`review_note`、`payload JSONB`、`payload_schema`（整数）、`created_by`、`updated_by`、`lock_version`、时间戳。
- 写入时用 `kind` 对应的 Pydantic 模型严格校验载荷，不允许多余字段，金额只接受十进制字符串。
- 启用时由 service 在事务内对同一 `(kind, scope_key)` 加 `SELECT … FOR UPDATE`，检查有效期是否与其他已启用版本重叠，重叠则返回 409 拒绝。部分唯一索引 `(kind, scope_key, version)` 防止版本号重复。
- 计算时按 `(kind, scope_key, status=active, 核价日期落在有效期内)` 唯一命中一条。

备选方案是每类规则建一套关系表（预计 10 张以上）。缺点是每次 Amazon 改费率结构都要做迁移，而这些规则的数量只有几十到几百行，用不上关系表的约束能力。所以选 JSONB。代价是数据库层不校验载荷内容，靠 service 校验和引擎测试保证。

### 决策 9：核价单与快照

- `pricing_sheet`：`id`、`owner_id`、产品名称、SKU、ASIN、来源链接、`status`（draft、saved）、`current_version_id`、`lock_version`、时间戳。
- `pricing_sheet_version`：`id`、`sheet_id`、`version_no`、`input JSONB`、`rule_refs JSONB`（采用的每条规则的 id、版本号和实际参数值副本）、`result JSONB`（每个市场 × 方案的状态、明细和结果）、`model_version`、`client_token`、`created_by`、`created_at`。保存后不可修改。`(sheet_id, client_token)` 唯一，用来防止重复提交。
- `pricing_selection`：`sheet_id`、`market`、`version_id`、`option_key`、`selected_by`、`note`、`selected_at`。每个市场只有一条，换选时覆盖并留痕到 `pricing_selection_log`。

保存版本时，服务端按输入**重新计算**，不接受客户端传来的结果。草稿只保存输入，不保存结果。「规则已更新」标记在查询时比较 `rule_refs` 与当前启用版本得出，不需要后台任务。

### 决策 10：接口

- `POST /api/pricing/calculate`：无状态试算，返回结果和 `rule_refs`。
- `GET/POST/PATCH /api/pricing/sheets`：草稿的创建和修改带 `lock_version`，冲突返回 409。
- `POST /api/pricing/sheets/{id}/versions`：保存为新版本，带 `client_token`。
- `POST /api/pricing/sheets/{id}/copy`：复制核价单。
- `PUT /api/pricing/sheets/{id}/selections/{market}`：选定方案。
- `GET /api/pricing/sheets/{id}/versions/{vid}/export`：导出 CSV（UTF-8 BOM，方便 Excel 直接打开）。
- `/api/pricing/rules`：增删改查，加 `activate` 和 `retire` 两个动作。
- `GET /api/pricing/meta`：返回市场、币种、类目、货物属性等枚举。

列表接口都分页，并按 `owner_id = 当前用户` 过滤。访问他人的核价单统一返回 404，错误码为 `pricing.sheet_not_found`。

### 决策 11：权限

新增 `pricing:view`（试算、本人核价单）和 `pricing:manage-rates`（写共享规则）。读取规则只需要 `pricing:view`。迁移种子：`admin` 获得两项（admin 默认拥有全部权限，不放进 `SUPER_ONLY_PERMISSIONS`），`operator` 和 `analyst` 获得 `pricing:view`。前端把 `canViewUnreleased` 换成 `canViewPricing`，费用配置的编辑按钮按 `canManagePricingRates` 显示，后端逐个端点校验权限。

### 决策 12：站点与币种

`Site` 新增 `currency` 和 `currency_minor_unit` 两个字段，作为站点的静态属性。核价市场必须已在 `SITE_CATALOG` 中登记，并且有已启用的 `market_params`；**不要求**站点在 `ENABLED_SITES` 中，因为核价不依赖 ABA 数据。新增市场的流程：在目录中登记站点，再配置市场参数、汇率、佣金、FBA 费率和渠道。`extension/src/site-map.ts` 只镜像站点集合，不涉及币种，本次不用改。

### 决策 13：引擎是纯函数模块

`app/table/pricing/engine/` 不访问数据库，也不依赖 FastAPI。输入是已解析的规则对象和场景，输出是结果对象，带 `MODEL_VERSION` 常量。规则解析在 service 中完成。这样引擎可以用大量参数化单元测试覆盖边界，以后 #171 的 Agent 也可以直接调用同一个入口。

### 决策 14：初始数据

迁移只建表和写权限种子，**不写入费率数据**。另外提供两个脚本：

- `scripts/pricing_import_excel.py`：把原 Excel 的自发货渠道导入为**草稿**，载荷带来源单元格。
- `scripts/pricing_seed_drafts.py`：按 2026 年官方费率卡录入 US、GB、DE 的 FBA 费率、标准类目佣金和市场参数，同样只生成**草稿**，`source` 写官方文档 URL 和生效日期。

由维护人员在界面上逐项核对后启用。

实现时的数据来源：GB/DE 取 Amazon Europe Rate Card（2026-07-01，官方 PDF），德国取「DE Only」列（未加入中欧计划 CEP）；US 佣金取官方定价页；US FBA 配送费、仓储费和旺季费只找到二手来源（amzprep），在规则的来源和审核说明里写明，启用前必须用卖家后台收入计算器复核。汇率不预置。

### 决策 15：费用配置的编辑方式

汇率、市场参数、自发货渠道用结构化表单（渠道的重量区间、附加费是可增删的列表），因为这三类最常由运营按报价单维护。类目佣金和 FBA 费率的结构是「尺寸段 × 重量区间 × 价格段」，首版用 JSON 编辑，由后端按类别逐字段校验并指出错误路径；初始数据由种子脚本按官方费率卡生成，日常操作主要是核对、复制成新版本后修改。等 FBA 费率确实需要频繁手改时，再做表格编辑器。

### 迁移方案与对 `analysis` schema 的影响

- 手写一个 Alembic 迁移：在 `DATABASE_SCHEMA` 中新建 5 张普通表（`pricing_rule`、`pricing_sheet`、`pricing_sheet_version`、`pricing_selection`、`pricing_selection_log`），登记到 `V2_TABLES`，**不登记**到 `PARTITIONED_TABLES`（保留清理不得删除核价历史）。同时写入 `permission` 和 `role_permission` 种子。
- 不改动任何现有分析表、分区、物化视图或其索引。降级时删除这 5 张表和权限种子。
- 迁移到 head 后，在真实库上检查模型与库是否一致。

### 连接池、内存与索引

- 试算是 CPU 轻量计算：每个市场的分段点不超过约 50 个，方案不超过约 50 个，单次计算毫秒级，在请求线程里同步执行即可，不需要放进线程池。规则读取每次请求一到两次小查询，不常驻连接池。
- 索引：`pricing_sheet(owner_id, updated_at desc)` 用于记录列表；`pricing_sheet_version(sheet_id, version_no)` 唯一；`pricing_rule(kind, scope_key, status)` 用于计算命中。数据量预计在千到万行，执行计划不构成风险。
- 导出按单个版本生成，体量为 KB 级，流式输出。不影响导入链路的连接预算和咨询锁。

## Risks / Trade-offs

- [费率数值过时或录入错误，导致利润算错] → 规则必须填来源和生效期才能启用；结果明细逐项显示采用的规则和来源；规则更新后，历史记录提示重新核价；初始数据只生成草稿，必须人工核对后启用。
- [FBA 尺寸分段模型覆盖不到特殊品类，如服装尺寸段、危险品] → 超出范围时状态为「不适用」，可手填配送费兜底；危险品作为货物属性标记，FBA 规则未配置对应费用时为「不适用」。
- [关税不确定] → 不给默认值，未填则为「待补资料」。结果中同时显示「关税占利润的比例」，提示敏感性。
- [JSONB 载荷结构漂移] → 用 `payload_schema` 记录版本，读取时按版本解析；载荷模型变化时写迁移脚本升级草稿，已保存快照保留原样。
- [本设计的行业默认口径不符合团队实际做法] → 默认值全部是可编辑的市场参数或场景输入，修改不需要发版；`docs/pricing` 中写清每个默认值的来由。
- [范围大，单个 PR 难以评审] → 按任务分组提交（引擎、存储与接口、前端），在同一个变更分支里多次提交；可以先合引擎和后端，前端紧随其后。

## Open Questions

- 广告预留 %、退货损耗 %、结汇手续费 %、默认在仓月数的初始值：草稿种子建议用 10%、3%、1%、2 个月，以团队实际数据为准，可以在费用配置中修改。
- 是否需要「海外仓自发货」模式（头程到海外仓再派送）：本设计可以把它表达成「头程＋渠道固定派送费」的自发货渠道，暂不单独建模式。
