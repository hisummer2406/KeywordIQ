## Context

竞对监控的 Amazon 侧目前是一具空壳：`competitor_seller` 有主体、有关注关系、有
`baseline_at` 列，但没有任何商品数据写进来，界面状态恒为「待建立基线」。独立站那条线
（`dtc-store-monitoring`）已经把上新流的形状做出来了，`NewArrivalsTab` 里 `AMAZON` 分支
预留着但恒无数据。

Amazon 侧拿不到数据的原因不是没做，是**没有可用的拉取式数据源**：SP-API 只能查自己授权的
账号，PA-API 已弃用且从无按卖家 ID 检索的操作，自建服务端爬虫经核算与 Keepa 同量级成本却
额外背负维护与封号归零风险（issue #56 已逐条排除）。剩下的路是**浏览器插件被动采集**：
运营本来就在手动点开收藏的 `me=` 页面，把这个已经发生的动作结构化存下来，零基础设施成本、
不新增反爬敞口。

本变更做这条路的服务端侧。采集端（Chrome 插件）不在范围内，但它要照着本变更定下的端点契约
写，所以契约的每一个决定在这里都得说清楚。

一个已实测的前提**本次有意不处理**：Amazon 店铺搜索结果按操作者账号的收货地址过滤
（2026-08-31 抽样 120 家，日本地址下 92 家显示无货，但抽查 30 家有 16 家仍在正常卖货，
真实存活率回推约 64%）。本变更把采集时的配送地区随上报存下来，但**不据此做任何判定**。

## Goals / Non-Goals

**Goals:**

- 一份插件可以照着写的、稳定的上报契约：幂等、有配额、失败逐条可解释。
- 「卖家 → 在售 ASIN」落库，承载 `first_seen_at`，为 ABA 联查（P2 的方向 A/B）备好按 ASIN
  回查的地基。
- 基线判定真正生效：首批上报不产生假上新。
- 上新流合并两类来源，Amazon 侧时间语义标注为「发现于」。

**Non-Goals:**

- **不做 Chrome 插件本体**（P3a 采集端）。
- **不做下架判定**，不存"这次没见到"的差集。
- **不做与 ABA 关键词的联查**（P2）：不补 `top2/top3_product_id` 索引、不加「竞对新品」筛选。
- **不做 Keepa provider**（P3c）与后台自动巡检（P3b）。
- **不碰日报/周报导入路径**与 ABA 查询层。
- 不为本功能引入新的基础设施（无 Redis、无 Celery、无新的定时器）。

## Decisions

### 决策 1：推模型，端点接收上报；不套进拉取式 Provider 协议

插件主动 `POST` 上报，后端只有一个接收端点，**不实现** issue 里那个
`SellerListingProvider.fetch_listings(seller_id, marketplace)` 协议。

两者的形状根本不同：拉取式是「后端决定何时抓谁、等结果返回」，而插件采集是「运营碰巧打开了
哪一页，就上报哪一家」——后端既不能决定时机，也不能要求完整性。强行统一成一个协议，代价是
让接收端假装自己发起过一次拉取，而"这次拉取覆盖了什么"这个问题在推模型下没有答案。

将来若接 Keepa（P3c），那一条按拉取式协议单独实现，两套并存、各写各的表行；共享的是
`competitor_seller_asin` 这张表与上新判定，不是调用形状。

### 决策 2：不建 `competitor_asin_snapshot` 分区表

issue #56 的数据模型一节写了这张按月分区的快照表（估算 4400 万行/年）。**本变更有意不建**，
理由是它的前提在被动采集下不成立。

快照要回答的是「某时刻这家店在售的是哪些品」。定期全量抓取下这个问句有意义；被动采集拿到的
是**部分捕获**——运营点开 `me=&s=date-desc-rank` 通常只看第一屏，翻到第几页取决于他当时
在找什么。把每次捕获存成快照，存下来的是「运营那天翻了几页」，而它长得**和「这家店只有 18
个品」一模一样**，没有任何地方会报错。这与独立站那条铁律是同一个道理：下架判定只在
`catalog_complete` 为真时做，而被动采集永远不完整。

改为建 `competitor_asin_report`：**一次上报一行**的观测元数据（谁上报的、何时、哪个卖家、
本次多少条、采集时的配送地区、页面上下文）。它回答的是「这个卖家的数据有多新、是怎么来的」
——这在覆盖率取决于人的浏览习惯时,是界面必须能说清的事。量级是每卖家每次浏览一行，与
快照差两个数量级。

将来若 P3b/P3c 落地了真正的全量拉取，那时再建快照表，且届时它有 `catalog_complete` 这类
可信度标记可依托。**现在建等于先造一份没法解释的历史数据。**

### 决策 3：粒度是 `(seller_id, site, asin)`，不是 issue 写的 `UNIQUE(asin, marketplace)`

issue 的数据模型把 `competitor_asin` 定义为按 `(asin, marketplace)` 唯一。本变更改为
以 `(seller_id, site, asin)` 为主键。

因为上新这件事的主语是卖家：**同一个 ASIN 可以被多个竞对同时在售**（跟卖是 Amazon 的常态），
而「A 店首次出现这个品」与「B 店首次出现这个品」是两件独立的事，各有各的 `first_seen_at`。
按 ASIN 全局唯一存一行，第二家店的上新会被第一家的记录吃掉——表现是上新流里少条目，而少的
恰恰是"跟卖"这种运营最想知道的动作。

代价是同一 ASIN 在库里可能有多行。这不影响 P2 的 ABA 联查：那条路是按 ASIN 反查
`dim_product` 与事实表的 `top1/2/3_product_id`，多行反而正好回答「这个词位上的品，我关注的
哪几家在卖」。

### 决策 4：基线 = 第一次上报，`baseline_at` 一旦落定不再改动

某卖家的首次上报把 `baseline_at` 写成该次上报时刻（`COALESCE` 保护，后续上报不覆盖），
该批 ASIN 照常入库但**不进上新流**；之后 `first_seen_at > baseline_at` 的才算上新。

这与独立站的 `first_fetch_at` 是同构的，连失败形态都一样：没有这一列，新关注一个卖家的首刷
会把它全部在售品判成今日上新——issue #56 估算导入 2657 家后首刷瞬间产生约 12 万条假上新，
功能当场废掉。

**`baseline_at` 落定后被改动是这条路唯一能造成大面积假数据的方式**（改了会让首批那些品在
下一次查询里全部涌进上新流），所以写入用 `COALESCE(baseline_at, :now)`，不是无条件赋值。

### 决策 5：不做下架判定

被动采集的目录恒不完整（决策 2），因此**"上报里没有它"不等于"它下架了"**。表里不设
`delisted_at`，查询侧不做差集。

这是独立站那条铁律的直接推论。独立站有三道完整性判据（每页 200 + 空页终止 +
不少于 `/meta.json` 声称的商品数）才敢判下架，被动采集一道都没有。

### 决策 6：写共享层的授权判据落在私有关注关系上

`competitor_seller_asin` 是**共享层**（与 `competitor_seller` 同层，不带 `user_id`），但
上报端点只接受**上报者本人已关注**的 `(seller_id, site)`：不在自己的 `user_seller_watch`
里就拒绝该条，并逐条附原因。

不这么做，任何持有令牌的用户都能往共享层灌任意卖家的任意 ASIN，而共享层的数据是所有关注者
共用的——一个人污染，全体看见。这与 CRUD 层签名强制带 `user_id`、API 层永不从 Query 取
`user_id` 是同一条纪律（issue #56 的「账号过滤不能靠前端」）。

认证沿用现有 JWT，插件用已有的 `POST /api/auth/token` 换令牌，**不新增长期 API key**。
代价是令牌 24 小时过期、插件需要重新登录；新增一种长期凭证是独立的安全决策，不该为省一次
登录顺带引入。

### 决策 7：上报同步落库，不走后台任务；幂等靠 `ON CONFLICT DO NOTHING`

单次上报条数上限 `COMPETITOR_MAX_REPORT_ITEMS`（默认 200，一页搜索结果约 48~60 个品，
留三倍余量），**超限整批拒绝不截断**——截断会让"这次见到了什么"变成一份沉默的残缺记录，
而它与"这家店只有这些品"长得一样（同决策 2）。

这个体量一条 `INSERT ... ON CONFLICT DO NOTHING` 就写完了，走异步会话即可，不必进后台任务，
也不必占同步池。重复上报同一批 ASIN 不产生新行、**不改动 `first_seen_at`**——幂等在这里
不是锦上添花：运营刷新一次页面插件就会再报一次，若每次都更新 `first_seen_at`，一个老品会
因为被重新看到而跳进"今天的上新"。

`title` / `image_url` 同样只在首次写入时落定（只增不改）。价格、BSR、评价数**本变更不存**
——它们随时间变化，要存就得像独立站价格那样单开一张仅在变化时追加的表，而目前没有任何消费方
（上新流主列表只放两类来源的交集字段）。留给采集端扩展后再议。

### 决策 8：上新流在 SQL 里合并两类来源，不在应用层归并两页

`new_arrivals_stmt` 改为对两个来源各自做统一投影（来源、来源键、来源名、商品键、标题、
图片、时间、时间语义）后 `UNION ALL`，再统一 `ORDER BY at DESC` 与分页；`total` 对同一个
子查询计数。

不各查一页再在 Python 里归并：那样第 2 页会重复或漏掉条目（每个来源自己的 offset 与合并后
的全局序号对不上），而这种错误在界面上表现为「某条上新出现两次」，极难归因——与
`site_data_stats` 那两个预存值当分界线的道理相同。

执行计划上两侧都走各自的 `(关注关系 → 主体 → 商品)` 三连 join，Amazon 侧新建
`idx_competitor_seller_asin_new (seller_id, site, first_seen_at)` 支撑时间窗过滤与排序。
量级：单用户关注上限 3000 家 × 每家几十个品，且恒有 `first_seen_at > now() - N days`
这道窗口过滤，实际参与排序的行数以百计。

### 决策 9：迁移是两张普通表，走 autogenerate 后人工核对

两张都是普通表——**MUST NOT 登记进 `partitioning.PARTITIONED_TABLES`**：登记即被保留清理
按 `HOT_WINDOW_MONTHS` 整月 `DROP`，而"这个品是什么时候第一次见到的"越久越值钱（它正是上新
判定的依据），那个三个月窗口是为八亿行的 ABA 事实表定的。

两张表**必须登记进 `migration_scope.py` 的 `V2_TABLES`**，否则 autogenerate 既看不见也不
报错，对模型改动一律回答"没有差异"；`test_conventions.py` 会拦住漏登。迁移目标 schema 为
`analysis`（由 `database.Base` 的 metadata 统一提供）。列注释参与 autogenerate 比对，模型
里的注释文本要与迁移一字不差。

### 决策 10：配送地区存下来，但不参与任何判定

上报体带 `ship_to_region`（采集时账号的配送地区，如 `US` / `JP`），存进
`competitor_asin_report`。**不据此过滤、不据此判定存活或下架**。

因为那条实测结论（日本地址下 92/120 家显示无货，实际存活约 64%）意味着：**在非目标市场
地址下采到的"没见到"是账号设置的产物，不是事实**。而本变更本就不做下架判定（决策 5），
所以这个字段现在只有一个用途——出问题时能分辨"这批数据是在什么账号设置下采的"。运营账号
改成美国地址之后，历史数据也能据此区分。

不存它的代价是不可回溯：数据入库后无从知道当时的账号设置，与"币种事后补不回来"是同一类。

## Risks / Trade-offs

- **[覆盖率取决于人的浏览习惯]** → 只有被点开的卖家才有数据，且新鲜度参差。缓解：
  `competitor_asin_report` 记录每次上报时刻，界面按卖家显示"最近采集于"，从不把"没有数据"
  呈现成"没有上新"；卖家状态区分「待建立基线」与「监控中」。
- **[基线之后的第一次上报可能夹带旧品]** → 运营首次只翻了第一屏，第二次翻到第三屏，那些
  更老的品会以"新发现"的身份进入上新流。缓解：这是"发现于"这个措辞本身承担的语义（既有
  spec 已要求 Amazon 侧标注为「发现于」而非「上架于」）；界面不得改口。无法在数据层消除。
- **[共享层被污染]** → 决策 6 把写入限制在自己关注的卖家上，降低但不消除风险（关注是自助的）。
  缓解：上报按 `(user_id, seller_id, site)` 留痕，可追溯到具体账号。
- **[上报端点是新的对外写入面]** → 它接受来自浏览器扩展的请求。缓解：沿用现有 JWT 鉴权与
  `competitor:view` 权限点；条数上限拒绝式；不接受 `user_id` 之类的身份参数（一律从令牌取）。
- **[与 issue #56 数据模型的偏离]** → 决策 2 与决策 3 都与 issue 正文写的不同。缓解：两条
  偏离的理由都写在此处，issue 里那份是在"定期全量抓取"前提下写的；本变更归档时同步回 issue。

## Migration Plan

1. 新增模型 → 登记 `V2_TABLES` → `alembic revision --autogenerate` → 人工核对生成的 DDL
   （两张普通表、schema 为 `analysis`、列注释与模型一致、**不出现** `PARTITION BY`）。
2. `alembic upgrade head`；`test_v2_integration.py::test_models_match_migrated_schema` 必须
   对迁移后的库产出**空** autogenerate 结果。
3. 后端与前端一并上线（v2 分支整体发布，不逐个发布）。
4. 回滚：`alembic downgrade -1` 直接 `DROP` 两张新表——它们不被任何既有路径写入，删除不影响
   ABA 与独立站数据。上新流的两来源合并需与迁移同版本回滚（否则查询会引用不存在的表）。

## Open Questions

- 插件的登录形态（弹窗内登录 vs 复用已登录的 Web 会话）留给采集端那次决定；本变更只要求
  请求带合法 JWT。
- 运营账号的收货地址前提何时解决——本变更不依赖它，但在它解决之前，Amazon 侧上新流的覆盖
  面偏低是预期内的（决策 10）。
