## Context

趋势小图 `frontend/src/components/TrendSparkline.tsx` 目前把排名数值藏在悬浮提示里，
颜色则由窗口首尾之差决定（`values[n-1] < values[0]` → 绿）。「排名变化」列
`frontend/src/pages/Analysis/columns.tsx:28-37` 另有一套硬编码色值。两处语义相同、
色值不同，且口径本就不同，叠加后用户无从判断颜色差异意味着什么。

约束来自真实数据（dev 库 US 站 2026-08-08，41 万行）：

- 排名跨度 1 – 433,961；**75% 的行 ≥ 100000**，即标签常态是 `433,961` 这样的 7 字符
- 小图 168×52，所在列宽 190px；天视图 7 点、周视图 4 点
- 行高已由商品卡牌（56px 缩略图 + 文字）撑到约 100px

## Goals / Non-Goals

**Goals**

- 每点排名常驻可读，且七个六位数不重叠
- 升/降/无变化色值三处共享，"无变化"统一为蓝
- 不撑高表格行

**Non-Goals**

- **不改小图颜色的口径**。它继续表达整段走势，不改由 `ranking_change` 驱动
- 不改后端：`trend` / `trend_dates` 字段与含义不动，无接口变更、无迁移
- 不动悬浮提示承担期次的既有设计

## Decisions

### 决策一：标签交替置于折线上下两侧

七个 `433,961`（9px 字号下约 38px）等距排在一行需要约 294px，而可用宽度只有 168px。
三个可选解：

| 方案 | 结论 |
|---|---|
| 缩写为 `434k` | **否决**。4 字符能排下，但把 433,961 与 434,499 显示成同一个值；排名的精度正是它的意义所在，`433,961 → 433,500` 这样 461 位的改善会变成"没有变化" |
| 加宽列到 ~320px | **否决**。表格已有 7 个定宽列合计逾千像素，再加 130px 会把商品卡牌列挤没 |
| **交替上下标注** | **采纳**。同侧相邻标签间距翻倍至约 52px，38px 的标签留有 14px 余量 |

代价是高度由 52px 增至 72px。因行高已被商品卡牌撑到约 100px，**这 20px 不产生任何
行高变化**——趋势列不是决定行高的那一列，这是本方案成立的前提。

标签用中性灰 `#595959` 而非升降色：折线已经承载颜色，数字再着色会与之相争，且七个
彩色数字会让"整段是红是绿"这个第一眼信息变得难找。

### 决策二：色值取深色一组

现有两组：列用 `#3f8600` / `#cf1322`，小图用 `#52c41a` / `#ff4d4f`。取**深色组**，
判据是对比度——同一组 token 要同时服务两列小字与一条 2px 折线，须由更严的场景决定：

| 色值 | 白底对比度 | 作正文 |
|---|---|---|
| `#52c41a` | ≈ 2.6:1 | 不达 WCAG AA（需 4.5:1） |
| `#3f8600` | ≈ 5.5:1 | 达标 |

深绿画 2px 线依然清晰，反之亮绿写字则偏淡，故深色组是唯一能同时满足两处的取值。

"无变化"取蓝 `#1677ff`（小图现值），**「排名变化」列的 `0` 因此由灰 `#999` 变蓝**，
波及约 15.7% 的行。这是本变更唯一一处用户可见的非新增改动，已单独确认。

### 决策三：token 放在组件目录而非全局主题

新建 `frontend/src/components/trendColors.ts` 导出 `TREND_COLORS`。不放进 Umi 主题
变量，因为这三个色值表达的是**业务语义**（名次升降），不是品牌色；放进主题会让它们
看起来可以被换肤，而换掉绿红会直接改变数据的含义。

## Risks / Trade-offs

**七个六位数的密度**。190px 单元格里放七个 `433,961`，可能读起来像噪音而非信息。
这一点无法靠推演定论，只能做出来看。若实际过密，退路按优先级：只标首尾与最值 →
缩写 → 加宽列。本变更先按全标实现。

**交替标注在折线陡峭处可能贴近线条**。标签不追随折线的 y 值，而是固定在图形上下两条
基线上，因此不会与折线交叠——代价是标签与其对应点的视觉关联弱一些，靠 x 对齐承担。

## Migration Plan

无。纯展示层改动，无数据、接口或配置变更，无需迁移，可直接部署与回滚。
