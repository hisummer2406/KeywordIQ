## Context

分析查询屏的筛选草稿由 `frontend/src/pages/Analysis/filters.ts` 的 `emptyFilters()` 产出，
当前所有筛选维度都是「不筛」，其中 `isNew: undefined` 表示「全部词」。这个工厂函数今天有
**四个调用点**，语义并不相同：

| 调用点 | 语义 | 受本变更影响 |
|---|---|---|
| `index.tsx:68` 初始草稿 | 「进屏时筛选长什么样」 | ✅ 要变 |
| `index.tsx:320` 首屏自动查询 | 同上（必须与初始草稿一致，否则表格与控件对不上） | ✅ 要变 |
| `index.tsx:248` `resetFilters` | 「重置按钮清成什么」 | ✅ 要变（决策 2） |
| `index.tsx:223` `submitScope` | 只用来从 `q` 推导 `keyword`/`asin` | ⚠️ 见决策 3 |

`is_new` 是导入时算定的既有列，`fact_daily` / `fact_weekly` 都有且带部分索引，查询层
（`analysis_crud.py`）本就支持 `is_new` 筛选，后端一行不改。

约束来自两条既有约定：**（1）** 「一个筛选维度在界面上恰好有一个入口」——这排除了新增
「恢复默认」按钮的做法；**（2）** 会话快照（`stateCache.ts`）在有快照时整段跳过初始化、
一个请求都不发，默认值不得穿透这道闸。

## Goals / Non-Goals

**Goals:**

- 首屏自动查询发出的条件带上「只看新词」，用户进屏第一眼就回答「今天有哪些新词」。
- 筛选控件的显示与实际发出的条件一致——控件必须显示为「只看新词」，不能表格是新词而
  控件显示「全部」。
- 「默认」这个概念在代码里只有一处定义，界面与请求体都从它派生。

**Non-Goals:**

- 不改会话快照的优先级：切走再切回仍复原用户自己的条件（决策 1）。
- 不新增「恢复默认」入口（决策 2 的直接后果）。
- 不改新词筛选控件的三态形态，不改后端 `is_new` 语义，不加迁移。
- 不给周视图定制默认值——周视图与日视图共用同一份默认筛选（决策 4）。

## Decisions

### 决策 1：默认值只在无会话快照的首次进屏生效，快照优先

沿用 `index.tsx:302` 那道 `if (restored) return;` 闸：有快照就整段跳过初始化，默认值
根本不参与。**不需要为此改任何代码**——默认值写在 `useCachedState('filters', ...)` 的
初值参数上，而有快照时该初值本就不被采用。

**替代方案（未采纳）**：每次进屏都重置为默认。它与刚落地的
`preserve-analysis-screen-state` 正面冲突——那条约定的全部价值就是切回来时条件与结果
原样保留、一个请求都不发；而「每次重置为默认」意味着切回来必须重查一次。两条同时成立
是不可能的，而快照那条已经写进规格并有测试守着。

### 决策 2：`emptyFilters` 更名 `defaultFilters` 并带上 `isNew: true`，重置回默认

只保留**一个**工厂函数，「进屏看到的」与「重置后看到的」是同一份值。

**替代方案（未采纳）**：拆成 `defaultFilters()`（含新词）与 `emptyFilters()`（全空），
重置用后者，另加「恢复默认」按钮。它让用户能一键回到全量榜单，但代价是过滤区出现两个
语义相近的按钮（「重置」与「恢复默认」），用户需要先理解两者差别才能选对——这正是
「一个筛选维度恰好一个入口」要避免的形态。取舍是：**放弃「一键回到全部词」，换取过滤区
不多出一个按钮**。用户仍可把新词开关手动拨到「全部」，只是多一次点击。

**更名不是洁癖**：`emptyFilters()` 产出一个带筛选条件的值，名字与事实相反。这类名字的
危害是它会被下一个人当作「中性基线」直接用——而这恰恰正在发生（见决策 3）。

### 决策 3：`submitScope` 改用显式中性值，不跟着默认走

`index.tsx:223` 的 `scopeOnly` 只是用来从 `q` 推导 `keyword`/`asin`，它产出的筛选值
随后被 `{...appliedRef.current, ...}` 覆盖掉——**除非 `appliedRef.current` 为 null**
（用户还没查过任何一次就直接点作用域栏的「立即查询」）。那种情况下 `scopeOnly` 会被
整体采用，此时带上默认的 `isNew: true` 恰恰是想要的行为。

因此这一处**不需要改动**，但要在代码注释里写明它依赖 `defaultFilters()` 的值——否则
将来有人改默认值时不会想到这里也跟着变。

### 决策 4：周视图沿用同一份默认，切换视图不动筛选

`is_new` 在 `fact_weekly` 上同样存在，周视图筛新词语义成立（「本周新出现的词」）。
更重要的是：现有交互里改站点/视图只重拉日期与类目清单、**不动筛选草稿也不重查表格**，
加一条「改视图会悄悄清掉新词筛选」等于引入一条隐形规则，用户改视图后会发现筛选莫名变了。

### 决策 5：测试里的「中性基线」改为显式传值，不新增测试专用工厂

`filters.test.ts` 有约 20 处把 `emptyFilters()` 当中性基线用，其中
`filters.test.ts:99-101` 直接断言基线产出的 `is_new` 为 `undefined`。默认值一变，那条
断言必红——**这是好事，它正是这次改动应该被察觉的地方**。

处理方式是把该组改成显式传三态（`isNew: true` / `false` / `undefined`），各自断言映射
结果；另加一条独立用例断言「默认草稿的 `isNew` 是 `true`」。其余把基线当「其他维度不筛」
用的地方不受影响——它们断言的是各自那个维度的映射，多一个 `is_new: true` 不改变结论。

**替代方案（未采纳）**：导出一个 `neutralFilters()` 专供测试。为测试而存在的生产代码
是负债，且它会重新制造决策 2 刚消灭的那种「两个相似工厂，不知道该用哪个」。

## Risks / Trade-offs

- **[用户想看全量榜单时多一次点击，且没有任何提示告诉他默认是筛过的]** → 新词筛选控件
  本就常驻在过滤区且显示当前值，进屏即显示为「只看新词」，状态是可见的。这是决策 2 的
  自觉代价，不是遗漏。若后续反馈显示这一步摩擦过大，加回「恢复默认」是独立的小变更。

- **[「今天没有新词」与「查询出错/条件筛没了」在空表格上仍可能混淆]** → 现有
  `scopeHasNoDates` 只区分「作用域无数据」，不区分「筛选把行筛没了」。但本变更不使这件事
  变糟：带筛选查出 0 行时照常显示「搜索结果：0」，与用户手动拨新词筛选查出 0 行完全一致。
  不在本变更内扩大空状态语义。

- **[首屏自动查询的性能特征改变]** → 由无筛选路径转为带筛选路径，两点后果：分页总数
  不再走 `site_data_stats` 的 O(1) 预存值，改为 `count_filtered` 精确实算（实测热缓存
  日报 168ms、周报 242–375ms，可接受）；且**掉榜行会全部消失**（任何筛选一生效，掉榜行
  在锚定期没有行可匹配），首屏因此只有在榜新词。后者是既有约定的必然结果、界面已有
  说明，但值得在实现时确认首屏那次查询的掉榜提示文案仍然成立。

- **[改名波及面比功能改动大]** → `defaultFilters` 的重命名触及 4 个生产调用点与约 20 处
  测试引用。风险是机械的、由 `tsc` 全量兜底：漏改一处即编译不过，不存在静默失败。

## Migration Plan

纯前端默认值改动，无数据库迁移、无接口变更、无配置项。回滚即回滚该次提交；已发出的
查询与已落库的数据不受影响。会话快照带 `CACHE_VERSION`，本变更**不改状态形状**（只改
初值），无需 +1——快照里存的是用户自己的条件，复原后仍然有效。
