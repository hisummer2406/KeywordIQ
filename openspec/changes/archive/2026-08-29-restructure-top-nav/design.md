# 设计决策

## 决策 1：`侵权查询` 进顶栏，而不是先隐藏

两个屏都没有数据源，进顶栏意味着**产品最空的一块变成最显眼的一块**——五项里有一项点进去
写着「数据源尚未接入」。备选是保留路由但 `hideInMenu`，等接上数据源再放出来。

选进顶栏，理由是这两屏的存在本身是给内部人看的路线图信号（「这块在做」），藏起来这个信号
就没了，而占位屏自己已经把话说清楚了、不会让人误以为有数据。代价是自觉承担的。

## 决策 2：`关键词工具` 保持一级菜单，不并进 `ABA数据选品`

按数据域，增长榜与词库和分析查询屏是同一批事实表，并进去最干净。**否决它的是布局代价**：

`src/app.tsx` 是 `layout: 'mix'` + `splitMenus: true`——顶层节点**有子项就长出左侧栏，
没子项就全宽**。`/analysis` 与 `/competitor` 今天是单页顶层，全宽。

分析查询屏是全产品最宽的表（指标列 + 走势小图 + 三个历史排名列）。给它挂上 ProLayout 那条
约 208px 的侧栏是净损失，而且是**永久**损失：横向裁掉的列找不回来。这与「我的词库」屏
拒绝把 GroupBar 做成侧栏、竞对监控屏拒绝侧栏形态是同一笔账，只是换了个地方付。

留下的代价是诚实的：词库的入库入口在分析屏，用户点「加入词库」后要去另一个一级菜单看结果,
这条流程跨了顶栏。可接受——加入词库是低频动作，而分析屏的宽度是每次查询都在付的。

## 决策 3：权限点改名 `keyword:view`，而不是保留 `toolbox:view` 或删掉

三个备选：

| | 代价 |
|---|---|
| 原样保留 | 留一个叫 toolbox 却不对应任何叫「工具箱」的东西的码，下一个人得翻 git 才知道为什么 |
| 改名 `keyword:view` | 一条迁移；**没有**解决「它不区分任何人」——三个角色全都有它 |
| 删掉、并进 `analysis:view` | 同样一条迁移，且减少一个权限点；但对自定义角色是收窄风险 |

选改名。它保住了一件事：**将来若要限制某人只看分析屏、不看关键词工具，这个开关还在**。
并进 `analysis:view` 会把那个可能性一并删掉，而删掉容易、加回来要再走一次迁移。

「它今天不区分任何人」不是删除的充分理由——`user:manage` 被删是因为它**勾了也不生效**
（后端根本不读它），而 `keyword:view` 是真执行的，只是内置角色恰好都授予了。这两件事
不一样，不要混为一谈。

### 与既有 spec 的一处字面冲突

`toolbox-navigation` 现有场景写着「系统中不存在名为 `library:*` 或 `keyword:*` 的权限点」。
它当初禁的是**给我的词库单开一个权限点**（授权粒度问题：「禁止某人管理自己的收藏夹」不是
真实需求），不是禁这个前缀。`keyword:view` 是容器级共用点、同时覆盖两屏，没有违反原意。

但字面字符串确实撞了，下一个人看到 `keyword:view` 会以为那个决定被推翻。所以 spec delta
里**把那条场景改写成禁止逐屏权限点**（`library:*`、`growth:*`），并写明容器点为什么叫这个。
不改写就是留一条自相矛盾的 spec。

### 迁移方案

`role_permission` 按 `permission.id` 关联（见 `app/user/rbac_model.py`），不是按 code。
所以改名是 `analysis.permission` 上的**一行 UPDATE**（`code` 与 `name`），角色的授予关系
一行都不动，**没有人的可见范围发生变化**。降级同样是一行 UPDATE，完全可逆。

迁移不 import 应用代码（沿用既有约定），code 字符串在迁移里硬编码；`permissions.py` 与
迁移两处同步改。

## 决策 4：旧地址只为有数据的两屏留重定向

`/toolbox`、`/toolbox/growth`、`/toolbox/library` 三条重定向到新地址，`hideInMenu`。
两个占位屏**不留重定向**——没有人会去书签一个写着「数据源尚未接入」的屏。

不做成前缀通配是因为 umi 的 routes 不支持，逐条列意味着这份路由表会越来越长；只留三条是
在「不让书签落空」和「路由表可读」之间的取舍，与 `/upload` → `/upload/file` 那条同一判据。

## 决策 5：后端 API 前缀与包名一并改，但独立成一组任务

`/api/toolbox/growth` 挂在一个叫「关键词工具」的菜单下，是决策 3 要消灭的同一种分叉，
只是低了一层。SPA 是这些端点的**唯一消费者**且与后端同版本发布，改名没有兼容负担。

独立成第 3 组任务（而不是散在各组里），是为了让它可以被整组砍掉：若评审认为「改 UI 结构
的同时改 API 面」混了两件事，删掉第 3 组，前两组仍然自洽——代价是留下前缀分叉，届时
`app/table/toolbox/` 的模块 docstring 要写明它现在服务的是「关键词工具」。

## 不涉及

- **数据库表结构**：只改 `permission` 表的一行数据，无 DDL。
- **查询与导入**：不改任何 SQL、索引、执行计划、连接池配置与内存占用。
- **权限执行方式**：仍是逐路由 `require_permission(code)`，无全局中间件。
