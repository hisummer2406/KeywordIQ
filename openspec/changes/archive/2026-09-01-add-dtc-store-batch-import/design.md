## Context

`dtc-store-monitoring` 已有单条添加入口（`POST /stores`：规范化域名 → 探测
`/meta.json` 判 Shopify 并取币种 → 建站点行 + 建关注关系）。本变更只是把这条路径批量化。

范围小、决策少，故本文只记三处「不这么做会怎样」不显然的地方，其余照既有路径写。

## Goals / Non-Goals

**Goals:** 一次性初始装载的批量入口；逐条可解释的结果。

**Non-Goals:** 不新增表、迁移、配置项、权限点、依赖；不做异步任务；不改单条路径。

## Decisions

### 1. 一步完成，不做预览 + 确认

判据是**这个操作可不可逆**。卖家侧两步流的存在理由是 `replace_group` 会清空整组重建，
以及 2657 条来自书签文件、用户不知道里面有什么。本能力两条都不成立：用户粘的是自己
知道的域名，加错了取关一次点击、已抓到的数据还留着。

*备选*：照搬两步流。要新增预览 token、暂存行与过期清理，为一次性需求付这份成本不值。

### 2. 结果按「输入行」组织，不按「站点」组织

响应里每一条对应用户粘进来的**一行原文**，而不是规范化后的域名。被拒绝的条目根本得不到
域名，只能用原文回指；能加入的条目若只回域名，用户也无法把它与自己粘的那一行对上
（`https://www.example.com/products/abc?utm=x` 与 `example.com` 看起来不像同一个东西）。

同一批里重复的行按规范化后的域名去重，只处理一次。

### 3. 并发探测用信号量，不用 `asyncio.gather` 直接铺开

每条要打一次 `/meta.json`。串行几十条是分钟级，必然超时；无上限并发对着几十个不同站点
同时发请求，既像异常流量也会让本机连接数失控。用 `asyncio.Semaphore(8)` 限流，
**所有条目共用同一个 `AsyncClient`**（连接池复用）。

单次条数上限取 200：按并发 8、单条约 1 秒估算，最坏约 25 秒，仍在一次请求可承受的范围内，
不需要引入异步任务。超限**整批拒绝**，与仓库其余上限一致。

## Risks / Trade-offs

- **[批量请求耗时可达十几秒]** → 界面要有明确的加载态与「正在探测 N 个站点」的提示；
  条数上限保证它有界。若将来真需要更大批量，那时才是引入异步任务的时机。
- **[一批里少数条目卡在慢站点，拖慢整批]** → 探测沿用既有的超时与重试设置
  （4xx 不重试），单条最坏耗时有界，因而整批也有界。
- **[部分成功的语义]** → 请求整体返回 200，成功的已写入、失败的在 `rejected` 段。
  这不是「静默失败」——每一条都有明确归属，且写入本身可逆。

## Migration Plan

无迁移、无 backfill。新端点不影响既有端点；前端在既有弹窗里加一个 tab。
回滚即回退代码。随 V2 整体上线。
