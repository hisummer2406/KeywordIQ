## Context

`POST /oss/upload-credentials` 有两类调用者，对「落一条 `UPLOADING` 批次」这个副作用的
需求正相反：开始新上传需要它，续签凭证不需要。两者先后独立落地（续签 `dd7fb40` 在
2026-08-01，落库副作用 `a0e8198` 在 2026-08-12），后者没有回头看端点还被谁调用。

`ossUpload.ts:69-71` 的注释证明这是个盲点——作者当时已经意识到续签会拿到新 object key
并特意丢弃它，但那时端点还没有落库副作用，所以只防住了 key。

## Goals / Non-Goals

**Goals**

- 一次上传在库中只留一条批次记录，无论续签多少次
- 续签路径不放宽授权前缀校验

**Non-Goals**

- 不追溯清理已产生的幽灵记录（人工处理，见 tasks.md）
- 不改续签间隔、不改凭证有效期、不改回收阈值
- 不改「新上传必须先落库再交凭证」这条既有约束

## Decisions

### 决策一：用请求里的 object_key 区分两种调用

请求体新增可选 `object_key`：带了即为续签，不带即为新上传。

| 方案 | 结论 |
|---|---|
| **请求带 object_key** | **采纳**。语义显式（"给这个 key 续签"），且后端拿到 key 就能做前缀校验 |
| 另开 `/oss/refresh-credentials` | 否决。两个端点的 RAM 策略必须逐字同步，迟早分叉；而它们本就只差一个副作用 |
| 后端按 (site, period, report_date) 去重 | **否决**。同一期次的合法重传会被误当续签吞掉——用户重传一份修正过的文件，界面上不会出现新记录 |

### 决策二：续签复用既有 key，不生成新 key

续签所得凭证的 RAM 策略限定的是**前缀**而非具体 key，因此对正在写入的 key 依然有效。
后端不再为续签生成新 key，前端也就不必再"丢弃"它——`ossUpload.ts` 那段注释描述的
防御随之失去存在理由，一并删掉，否则它会误导下一个读者以为续签仍会换 key。

### 决策三：前缀校验与导入触发共用同一个函数

续签校验 SHALL 走 `oss_client` 里那个已被 `/oss/import` 与重导共用的前缀校验，不另写
一份。理由与重导那次相同：**少掉越权那道校验，这个端点就成了为任意 key 取得写凭证的
入口**——而它签发的是**写**权限，比重导（触发导入）更危险。

区别是续签 MUST NOT 要求对象已存在：续签发生在传输途中，此刻对象尚未 Complete，
`head_object` 必然查不到。因此只做前缀校验，不做存在性与大小校验。

## Risks / Trade-offs

**旧前端配新后端**：不传 `object_key` 的调用仍按新上传处理，即幽灵记录照旧产生。这是
可接受的——前后端同仓同发布，且新增的是可选字段，不会让任何调用失败。

**续签校验放宽了"对象须存在"**：如上所述这是必需的，代价是持有合法前缀内任意 key 的
调用方可反复取得写凭证。但该前缀本就是这次上传被授权写入的范围，未扩大权限面。

## Migration Plan

无迁移。请求体新增可选字段，向后兼容。已产生的幽灵记录不由本变更处理。
