## Context

分析查询屏是 V2 唯一的读侧界面，`frontend/src/pages/Analysis/index.tsx` 单文件 269 行，
承担作用域选择、筛选、排序、分页、导出全部职责。改造前的形态是"迁移期的最小可用"：
作用域三元组塞进 ProTable 的 `headerTitle`，筛选借 ProTable 自带的搜索表单与列的
`valueType` 表达。

这带来三个具体缺口（详见 proposal）：类目只能单选、条件即时提交、区间类筛选没有界面入口。

**约束**

- 后端查询层（`site-scoped-query`）已落地且经受住集成测试，作用域「站点 + 视图 + 日期」
  三元组是不可突破的边界。本变更 MUST NOT 触碰这条边界。
- RDS 是 2C4G，同时真正能执行的查询受核心数限制（约 4 个）。界面上每减少一次无意义的
  中间查询，都是直接的容量收益。
- 前端是 Umi Max + AntD Pro，现有页面除 `Login` 外都不引 `.less`，用 antd 组件与内联样式。
- 现有前端测试 26 条，其中 `pages/Analysis/index.test.tsx` 覆盖表格查询路径，本变更会改到它。

## Goals / Non-Goals

**Goals:**

- 查询屏重排为作用域 / 过滤 / 结果三段，条件与区域的语义一致
- 类目多选（后端支持 + 前端面板）
- 查询显式触发，消除条件编辑过程中的中间查询
- 暴露后端已支持但界面缺失的区间类筛选
- 把单文件拆成可独立理解与测试的几部分，条件转换逻辑做成纯函数

**Non-Goals:**

- 不改数据模型、分区、导入管线、保留清理
- 不改鉴权与权限点，不改错误契约与 ProTable 响应契约
- 不新增后端筛选维度（除类目由单值变多值外，筛选能力集合不变）
- 不做卖家精灵那些我们没有对应数据的指标（搜索量、展示量、点击量、SPR、标题密度）
- 不做筛选条件的保存 / 分享 / 我的模式

## Decisions

### 决策 1：`category_exact` 换成 `categories`，不双写

**选择**：`AnalysisSearchRequest` 移除 `category_exact: str | None`，新增
`categories: list[str] | None`；`_apply_filters` 用 `DimProduct.category.in_(...)`。

**为什么不保留 `category_exact` 做兼容**：它唯一的调用方是同仓前端的类目列下拉
（`frontend/src/pages/Analysis/index.tsx` 的 `category_exact: params.top1_category`），
前端在同一次变更内更新。保留它就多一条没人走的分支，而两条语义重叠的类目筛选并存时，
"同时传了会怎样"是一个必须回答又不该存在的问题。

**为什么不是在 `categories` 之外还留 `category`（子串）**：`category` 是模糊匹配，
与精确集合匹配用途不同（前者给"我不记得完整类目名"，后者给下拉勾选），保留。

**上限**：`categories` 加 `max_length=100`。类目数可达数百，无上限的 `IN` 列表会让
计划器在参数很长时放弃索引扫描。100 覆盖"勾一批类目"的真实用法，超过它更可能是
"全选"——而全选等价于不筛。

### 决策 2：草稿态与生效态分离，用两份状态而非一份加脏标记

**选择**：页面持有 `draft`（用户正在编辑的作用域 + 检索词 + 过滤条件）与 `applied`
（表格 `request` 实际读的那份，用 `ref` 承载，沿用现有写法）。「立即查询」把 `draft`
复制进 `applied` 并 `actionRef.reload()`。

**替代方案**：单份状态 + `dirty` 布尔标记，查询时读同一份。**否决**：一旦条件与表格
数据来自同一份状态，表格重渲染时就会读到尚未生效的条件，"当前显示的是哪组条件"
无法从状态里读出来，导出（复用最近一次查询体）也会跟着漂移。两份状态让"生效条件"
成为一个可以直接读、可以直接断言的东西。

**`draft ≠ applied` 的提示**由两份状态的浅比较得出，不需要额外的脏标记维护。

### 决策 3：作用域元数据即时刷新，结果查询显式触发

用户选择了"全部手动"。但站点 / 视图与日期 / 类目之间存在数据依赖：日期清单来自
`GET /scope`、类目清单来自 `GET /categories`，两者都以站点与视图为参数。

**选择**：站点或视图改变 → 立即重新拉取 `/scope` 与 `/categories`，更新日期选项
（并把日期默认跟到该站点该视图的最新一期）与类目清单、清空已勾选类目；**不** reload 表格。

**理由**：这两个请求打在 `site_data_stats` 与 `category_stats` 物化视图上，是小表查询，
与在事实表切片上的结果查询不是一个量级。而如果不刷新，用户会在一份属于上一个站点的
日期清单里做选择——那是一个必定失败或静默查错切片的操作。

排序、翻页、每页条数走 ProTable 自身的 `request`，即时生效：它们作用于已经确定的
结果集，不属于"条件"。

### 决策 4：ASIN 判定用格式而非用户选择，但判定结果必须回显

**选择**：`/^B0[A-Z0-9]{8}$/i` 命中走 `asin` 字段，否则走 `keyword` 字段；检索框旁
实时回显「按 ASIN 检索 / 按关键词检索」。

**替代方案 A**：框前加类型下拉。**否决**：多一次输入，且与截图的单框形态不符。
**替代方案 B**：后端加 `q` 字段做 `keyword ILIKE ... OR asin ILIKE ...`。**否决**：
`OR` 跨两张维度表的两个 trgm 索引，计划器通常退化为全切片扫描——在千万行切片上
这是一个慢查询工厂。格式判定在前端一行正则解决，代价是零。

**回显是这个决策的必要组成部分**，不是装饰：自动判定一旦不可见，用户搜不到东西时
无从知道系统搜的是哪个字段。

### 决策 5：条件转换做成纯函数，与 React 状态解耦

`pages/Analysis/filters.ts` 导出：

| 导出 | 职责 |
|---|---|
| `FilterDraft` | 草稿条件的类型 |
| `emptyDraft` | 初值 |
| `detectSearchKind(v)` | 检索框输入 → `'asin' \| 'keyword' \| 'none'` |
| `RANGE_PRESETS` | 各区间维度的快捷档位定义（档位名 → 上下界） |
| `toSearchBody(draft, scope)` | 草稿 + 作用域 → `SearchBody`，只带非空字段 |

这几件事是这次改造里唯一有分支逻辑的部分（判定、档位映射、空值裁剪），做成纯函数
可以用 vitest 直接测，不用挂 DOM、不用 mock 请求。剩下的组件就只剩渲染与事件传递。

### 决策 6：文件拆分边界

```
pages/Analysis/
├── index.tsx          编排：draft/applied、作用域元数据、request、导出
├── ScopeBar.tsx       顶栏：站点 / 视图 / 日期 / 检索框 / 立即查询
├── CategoryPanel.tsx  左：全部类目 + 带计数复选列表 + 按名过滤
├── FilterPanel.tsx    右：区间行 + 快捷档位 + 文本条件 + 收起展开
├── filters.ts         纯函数（决策 5）
└── columns.tsx        ProTable 列定义
```

三个展示组件都是受控的：接 `value` 与 `onChange`，自身不持状态、不发请求。
判断边界是否合适的标准——`FilterPanel` 能不能在不知道站点是什么的情况下工作？能，
它只认条件对象。`CategoryPanel` 需要类目清单，但清单由 `index.tsx` 传入而非自取。

### 决策 7：份额单位不做换算

库里 `top1_click_share` / `top1_conversion_share` 是 `Numeric(10,2)` 的百分数（0~100），
`ShareBar` 已按 `{v}%` 渲染。界面档位与手输值直接就是百分数，接口传的也是百分数。

**不引入 0~1 小数与百分数之间的换算**：换算点是最容易出现单向遗漏的地方（写的时候
乘了 100、读的时候忘了除），而这里根本没有引入它的理由。

### 决策 8：排名变化保留原始数值口径

`ranking_change` 为负表示排名上升（名次数字变小）。手输区间用原始数值，与表格
「排名变化」列一致；快捷档位用中文语义（上升 = `change_max: -1`，下降 = `change_min: 1`，
持平 = `[0, 0]`）承担可读性。

**不在界面上把符号翻转**：翻转后界面数值与表格列数值符号相反，用户拿表格里看到的
数字回填筛选就会得到相反的结果。

## 对连接池、内存与执行计划的影响

- **连接池**：本变更减少请求数（条件编辑过程中的中间查询消失），不增加。切换站点新增
  的两个元数据请求（`/scope` + `/categories`）打在 `site_data_stats` 与 `category_stats`
  上，都是小表，且改造前切换站点本来就会发这两个请求。池配置不动。
- **内存**：前端改动不涉及后端内存。导出路径（服务端游标 + 自建会话）不变。
- **执行计划**：`category = :x` 变为 `category IN (:x, :y, ...)`。`DimProduct.category`
  上的条件走的是 JOIN 后的过滤，`IN` 与等值在计划形状上同类；`max_length=100` 的上限
  防止参数列表长到让计划器放弃索引。带类目筛选的总数仍走 `FILTERED_COUNT_CAP = 10000`
  的封顶计数，路径不变。

## 数据库迁移

**无迁移**。本变更不动表结构、不动索引、不动物化视图——`categories` 只改请求 DTO 与
`WHERE` 子句的构造，`analysis` schema 的对象一个都没碰。

## Risks / Trade-offs

- **切站点后表格显示上一个站点的数据** → 由「条件已修改」提示缓解（`analysis-screen-layout`
  的第三条要求）。这是"全部手动"触发口径的固有代价，用户已知情选择。
- **移除 `category_exact` 是破坏性接口改动** → 唯一调用方是同仓前端，同一次变更内更新；
  部署以整体为单位，不存在新前端配旧后端的窗口。若真出现版本错配，请求体带 `categories`
  而后端不认，Pydantic 默认忽略未知字段，退化为"不按类目筛"——是可察觉的错误结果而非崩溃。
  这一点在部署顺序上要求**后端先于前端**。
- **ASIN 格式判定会漏判非 `B0` 开头的 ASIN** → 亚马逊现役 ASIN 绝大多数是 `B0` 开头，
  漏判的表现是"当成关键词搜"且界面已回显，用户可察觉。不为此引入类型下拉。
- **快捷档位与手输区间两套输入的状态同步** → 单向：档位写入区间值，手输清除档位高亮。
  区间值是唯一事实来源，档位只是它的一组预设写入方式。测试覆盖两个方向。
- **过滤区吃掉竖向空间，表格可见行数减少** → 过滤区可收起；收起状态不持久化（YAGNI，
  真有需求再说）。

## Open Questions

- 类目面板在类目数极多（数百）的站点下是否需要虚拟滚动？先用限高滚动 + 按名过滤，
