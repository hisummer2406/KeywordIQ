# 插件自动采集试点（#205 阶段 1）

## Why

运营现在必须一家一家打开店铺、翻页、点提交，结果大部分 Amazon 卖家长期停在「数据陈旧」。#205 决定先在一台常开的宿主机上，让现有插件每天自动采集已关注店铺，用 5 天真实运行验证可用率、访问受限次数和人工介入次数，再决定是否建设后端任务化（阶段 2）或转向 #203 的数据接口。

阶段 0 已人工确认：店铺页按「最新」排序（`s=date-desc-rank`）生效，所以只需每天看前几页，不必翻全店。

## What Changes

- 插件新增「自动采集（试点）」：默认关闭，在设置页开启。开启后由 `chrome.alarms` 每天定时触发，也可以手动「立即运行一次」。
- 每轮读取当前令牌对应账号的 Amazon 关注清单，逐店在后台标签页打开按最新排序的店铺页，只采前 N 页（默认 2），合并后用现有上报端点上报一次，店与店之间随机间隔 30–60 秒。
- 任一页解析为空或超时，这家店本次不上报；遇到验证码或访问拒绝，整轮立即停止并记录原因。
- 运行进度持久化，Service Worker 被回收或 Chrome 重启后可以接着做；每轮每店的结果记录在插件本地，设置页可查看并导出 JSON。
- 人工采集面板与其上报流程保持不变；自动采集打开的标签页不显示人工面板。
- manifest 新增 `alarms` 权限，版本升到 0.3.0。

## Impact

- 代码：只改 `extension/`，不改后端、数据库和前端；无迁移。
- 规格：`competitor-browser-collector` 新增自动采集相关要求（delta）。`competitor-asin-ingest` 和 `competitor-storefront-watch` 不变：首次自动采集静默入库、卖家行展示「自动采集」等改动留到阶段 2。
- 运行约束：试点只连本地开发后端，不写生产库（理由见 design 决策 1）。
- 风险：Amazon 已明确表示自动访问违反其使用条款（#205 阶段 0 记录），由用户做业务决定后推进；开跑前宿主机的网络出口须与卖家后台分开。
