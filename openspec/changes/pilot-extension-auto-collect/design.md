# 设计：插件自动采集试点

## 背景与边界

阶段 1 只验证一件事：在普通 Chrome 里，插件能不能每天无人值守地采完 10–20 家店，同时不被 Amazon 拦截。后端任务队列、租约、设备凭证、首次自动采集静默入库，都属于阶段 2，不在本变更内。

## 决策 1：试点只连本地开发后端

首次自动采集静默入库（Codex 复审第 1 条）要改 `competitor-asin-ingest`，本变更不做。如果试点直接写生产库，已有人工基线的卖家，首次自动采集时前两页里没见过的存量商品会被判成新发现，污染上新流。所以试点期间，插件的 API 地址指向宿主机本地的开发后端。

插件无法自己判断某个地址是不是生产，因此这是运行约束，不是代码约束：设置页的自动采集区块写明这一点，tasks 的开跑检查里也列了这一项。

## 决策 2：只采按最新排序的前 N 页

URL 形如 `https://www.<域名>/s?i=merchant-items&me=<卖家>&marketplaceID=<站点>&s=date-desc-rank&page=<n>`。`i=merchant-items` 是现有 content script 识别店铺页的条件，必须带上。

- N 默认 2，设置页可调为 1–5。每家店每天的访问量固定，与店铺大小无关。
- 翻页直接改 URL 的 `page`，不模拟点击。页面提示没有下一页时提前结束。
- 多页先合并再上报一次，沿用「多页先本地合并、一次请求上报」的规则；合并时仍受服务端单批上限约束，读不到上限这一轮就不开始。

## 决策 3：后台事件驱动的状态机

MV3 的 Service Worker 随时可能被回收，所以不在内存里 `await` 长时间的等待：

- 每一步都由事件推动：`chrome.alarms`（每日触发、店间间隔、页面超时）、`chrome.tabs.onUpdated`（页面加载完成）、`chrome.tabs.onRemoved`。
- 运行状态（队列、当前店、当前页、已合并条目、冻结的幂等键、结果）存在 `chrome.storage.local`，每次状态变化后立即写入。
- 页面加载完成后，后台通过 `chrome.tabs.sendMessage` 请 content script 解析；content script 回传条目、是否有下一页、页面是否被拦截，以及所在文档的随机标识 `docId`。
- 店间间隔和页面超时都用 `chrome.alarms` 实现。Chrome 对 alarm 的最小间隔是 30 秒，正好与 30–60 秒的店间间隔吻合。
- **翻页时只认新文档的回答**（PR #206 Codex P2）：翻页后，旧页面的重复 `complete` 事件可能在新页面加载完之前被处理，此时回答的仍是旧文档。后台记下上一次处理的 `docId`，同一 `docId` 再次回答就忽略，等新页面自己的 `complete`。不用 URL 里的页码核对，因为 Amazon 可能改写翻页后的地址。
- **看门狗**（PR #206 Codex P2）：一轮运行期间保留一个每分钟触发的 alarm。状态是「运行中」，却既没有当前店也没有「下一家」alarm，就补建「下一家」；正在采集却没有超时 alarm，就补建超时。这样即使在「保存状态」和「创建下一步 alarm」之间被回收，这一轮也不会卡住。一轮结束时清除看门狗，残留的看门狗触发时自行清除。

恢复规则：

- 后台启动或收到 alarm 时，如果状态是「运行中」但当前标签页已经不存在：还在采集阶段的，从第 1 页重新采这家店，丢弃已合并的部分；已进入上报阶段的，用同一个 `request_id` 重发，由服务端幂等保证不会重复记录。
- 页面超时（90 秒没有拿到解析结果）按访问受限处理，整轮停止。验证码页可能落在 content script 不注入的地址，超时是唯一可靠的信号，宁可多停也不要继续访问。
- 页面加载完成却拿不到 content script 的回答时不立即下结论：可能只是重复事件落在新旧页面交替之间。交给页面超时判断；一直没有回答，超时后整轮停止。

## 决策 4：被拦截时整轮停止，空结果不上报

| 情况 | 处理 |
|---|---|
| 页面出现验证码表单、「Access restricted」、「Robot Check」等文字，或页面超时（含 content script 一直无响应） | 整轮停止，记录原因 |
| 页头配送地址不是站点所在国（读到地址但没有该国邮编，如 "China"） | 整轮停止，记录页面上的地址。读不到配送地址时不据此停止 |
| 第 1 页解析为 0 条 | 这家店本次失败，不上报，继续下一家 |
| 超过单批上限 | 这家店本次失败，不上报 |
| 上报返回 401/403 且同步令牌失败 | 整轮停止（凭证问题，后面每家都会失败） |
| 上报返回 422（如该账号未关注这家店） | 这家店失败，继续 |
| 上报网络异常（重试耗尽） | 这家店失败，继续 |

## 决策 5：运行记录留在插件本地

每轮记录开始和结束时间、触发方式（每日或手动）、停止原因，以及每家店的结果（成功／失败原因、采集页数、条数、新发现数、耗时）。最多保留最近 30 轮。设置页显示最近一轮的汇总，并可导出全部记录为 JSON，用于统计 #205 的门槛指标。不新增后端接口。

## 决策 6：凭证沿用现有令牌

自动采集复用现有的令牌读取和 401 自愈逻辑（`handleCapture`）。网页 JWT 只有 24 小时有效期，无人值守跑不过一天。试点在本地开发后端为试点账号签发一个长有效期令牌，通过「手动填写令牌」填入。这只是本地试跑的权宜做法，可单独吊销的设备凭证留到阶段 2；文档里不把它描述成已收窄的凭证。

## 决策 7：不与人工采集混用

- 自动采集打开的标签页不显示人工采集面板。content script 加载时先问后台「这是不是自动采集的标签页」，是就不渲染面板。
- 自动采集不读写人工面板的「已采集未提交」暂存区，两边各自维护幂等键。

## 明确不做

- 后端任务队列、租约、设备凭证、首次自动采集静默入库、卖家行展示「自动采集」（阶段 2）。
- 发布到生产插件或修改生产配置。
- 失败自动重试整轮；每天只跑一轮，失败的店铺等第二天再采。
