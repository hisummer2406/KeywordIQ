## Context

`frontend/src/pages/Analysis/index.tsx` 的全部界面状态都是组件内的 `useState` / `useRef`，
挂载副作用 `useEffect(..., [])` 无条件执行首屏初始化。umi 4.6 没有 keepalive（`@umijs/preset-umi@4.6.82`
与 `@umijs/renderer-react@4.6.82` 里都没有这个特性），路由切换会真的卸载这个组件，
于是「状态全丢」与「4 个接口重发」是同一件事的两面。

这一屏有一条不能碰的既有架构：**草稿态与生效态是两份状态**（见 CLAUDE.md 与
`analysis-screen-layout` spec）。任何缓存方案都必须把这两份分别存、分别复原，
合并成一份就等于毁掉「表格现在显示的是哪组条件」这个可读性。

## Goals / Non-Goals

**Goals:**

- 切走再切回：状态与结果原样复原，零请求
- 首次进入与刷新页面的行为完全不变
- 恢复滚动位置
- 判定逻辑是纯函数，可用 vitest 直接测（与 `filters.ts` 同一路子）
- 不引入新依赖

**Non-Goals:**

- 不做跨会话持久化（不写 localStorage / sessionStorage）
- 不引入 KeepAlive 类方案
- 不改查询接口、查询语义、草稿/生效分离的架构
- 不修工具箱「持续增长市场」屏的同类问题（另开变更）
- 不做缓存过期策略（TTL、后台轮询失效）

## Decisions

### D1：会话内模块级缓存，不用 KeepAlive

**选**：新增 `frontend/src/pages/Analysis/stateCache.ts`，一个模块级变量持有快照。

**否决 `react-activation`（KeepAlive）**：语义上最接近小程序页面栈，连滚动位置都自动保留，
页面代码几乎不用改。但代价是一个第三方依赖 + React 18 并发特性下已知的兼容坑 +
组件实例常驻内存，而 umi 4.6 不原生支持它。更要紧的是它把「记住什么」变成隐式行为——
出问题时无从读出边界；模块级缓存里存了什么，代码里一眼可见。

**否决 umi `model`（`useModel`）**：`plugin-model` 确实已启用，但 model 的价值是**跨组件共享**，
而这份状态只有一个消费者。用 model 会把状态变成全局 store、把订阅关系与重渲染范围一并放大，
换不来任何东西。

### D2：write-through 写入，不在卸载时写

**选**：一个 `useCachedState(key, initial)` 钩子——初值从缓存读，`set` 时同步写回缓存。
`appliedRef` / `totalRef` 这类 ref 同样从缓存读初值、赋值处写回。

**否决「卸载时统一写快照」**：那依赖 effect cleanup 的执行顺序，React 18 下不可靠
（并发渲染可能触发额外的挂载/卸载对），而且失败是静默的——用户切走时状态没存上，
切回来看到默认值，与现在的 bug 长得一模一样，无从区分。write-through 每次改动都落盘，
没有「最后那一下没存上」这种状态。

### D3：请求短路的判据是请求签名，不是「有没有缓存」

ProTable 的 `request` 在**请求签名与缓存中那次完全相同**时返回缓存行，否则照常发请求。
签名 = 生效条件（`appliedRef.current`）+ 排序字段与方向 + 页码 + 每页条数。

判定写成纯函数 `sameRequest(a, b)`，vitest 直接测。**不能退化成「有缓存就不发请求」**——
用户切回来之后翻页、改排序都必须真的去查，那是新的请求，不是同一次。

### D4：滚动位置在行渲染完成之后恢复，且只恢复一次

复原路径上带一个「待恢复的滚动量」，在表格数据落到 DOM 之后（数据 state 更新后的
`useEffect`）执行一次 `window.scrollTo`，随即清掉标记。

**为什么不能在挂载时立刻恢复**：那时表格还是空的、页面高度不足，`scrollTo` 会被截断到
当前最大滚动量，停在一个与离开前不对应的位置——而这种错误没有任何地方会报错。

**为什么要清标记**：不清的话用户在本屏内自己滚动、触发一次重渲染就会被弹回旧位置。

### D5：登出时清空，挂在既有的三步登出上

`src/app.tsx` 的 `doLogout` 已经是「清令牌 → 清 initialState → 回登录页」，缓存清空
作为第四步加在同一处。那里是唯一的登出路径，与另外三步同生共死。

不这么做的后果很具体：同一标签页内 A 登出、B 登录，B 会看到 A 的查询条件与结果行。

### D6：缓存形状带一个版本号

快照对象带 `version` 常量，读取时版本不匹配即视同无缓存。开发期热更新改了状态形状后
残留的旧快照会以 `undefined` 的形式渗进 UI，表现为零散的空白控件，很难归因。
版本号让这类情况退化成「走一次正常初始化」。

### D7：复原不等于关闭后续请求

从缓存复原只跳过**挂载时的初始化**。既有的「改站点或视图立即重拉 `/scope` 与 `/categories`」
逻辑一行不动——那是用户的动作触发的，与本变更无关。

## Risks / Trade-offs

- **看到的是快照，不是最新数据** → 数据每天导一次，且「立即查询」是既有的显式刷新入口；
  spec 里写明返回时不刷新是**约定行为**而非缺陷。不做 TTL：多一个会自己变的时机，
  就多一份「为什么表格自己变了」的困惑。
- **滚动恢复时机踩不准** → 只在数据落 DOM 后恢复、只恢复一次；恢复逻辑与判定分离，
  时机错了表现在集成/手测中可见。
- **缓存形状随代码演进腐烂** → D6 的版本号；且缓存只活在会话内，发版后用户刷新即清空。
- **`useCachedState` 用错 key 会串状态** → key 集中在一处以字面量联合类型声明，
  写错即 TypeScript 报错，不留运行期发现的余地。
- **内存** → 一页最多 200 行 + 类目清单，几十 KB 量级，忽略不计。

## 对数据库与容量的影响

- **无数据库改动**，不涉及 Alembic 迁移，`analysis` schema 不变。
- **无 SQL 变化**，不影响任何索引或执行计划。
- **连接池是净减负**：切页产生的 4 个请求降为 0，异步池（`DB_ASYNC_*`，服务查询与鉴权）
  的占用只减不增。内存占用只在浏览器侧，服务端无变化。

## Migration Plan

纯前端改动，随 SPA 产物一起发布，无迁移步骤、无回滚数据风险。回滚即回退这一个提交。
用户侧无需任何操作——旧行为与新行为的差别只在「切回来还在不在」。
