## Context

竞对监控 P0（PR #57）只落地了关注清单本身。数据获取层在 issue #56 里排了三条路——
浏览器插件被动采集（P3a）、Keepa（P3c）、CSV 导入（已确认无数据源，排除）——但都卡在
未决前提上，导致「近 7 日上新数」这一列自上线起恒为占位符。

2026-08-31 用用户的真实浏览器与本机网络逐项实测了两条数据源，结论决定了本变更的范围：

**Amazon 侧（本变更不含）**

- 店铺页可读：`div[data-component-type="s-search-result"][data-asin]` 拿 ASIN，
  `h2` 拿标题，`.a-price .a-offscreen` 拿售价与原价，`data-cy` 属性（`title-recipe` /
  `price-recipe` / `reviews-block` / `delivery-recipe`）是比 class 名更稳的锚点；
  详情页可拿 BSR 与四级类目路径。约 140 次自动请求零验证码。
- **但拿不到上架时间**：试了 5 个 ASIN（跨美妆/家居/电子，BSR 从第 1 名到 15 万名），
  「Date First Available」字段在页面上根本不存在。整套 `baseline_at`、锁第 1 页、
  只做并集不推断下架的设计，都是为绕开这一条而存在的。
- **且实测撞到一个系统性污染**：用户账号收货地址是日本，120 家抽样里 92 家显示无货；
  但对这些「空店」查卖家资料页，**16/30（53%）有近半年的买家评价**，说明它们在正常
  卖货、只是商品被配送地址过滤了。真实存活率回推约 64%，不是表面的 23%。这个偏差的
  界面表现与「这些店没上新」完全一致，无法自行发现。

**独立站侧（本变更范围）**

- 书签里 17 个独立站域名 **17/17 在线，全部是 Shopify**，16 个 `/products.json` 可用
  （`de.molooco.com` 证书异常，`lumerosy.com` 偶发超时但可重试成功）
- 该端点直接给 `published_at` / `created_at` / `updated_at`，以及每个变体的
  `price` / `compare_at_price` / `sku` / `available` / `option1-3`
- 翻页可取全量目录：实测 leteimall.com 共 **1202 个商品、5 页**取完
- 单店规模实测：leteimall 1202 商品 / 6582 变体，blessrich 1241 / 9359，
  kydschoice 151 / 394。**平均 6.3 个变体/商品，中位 2~3，最大 169**
- 销量：`/products.json` 无任何销量字段；`/collections/all/products.json` **忽略**
  `sort_by`（三种排序返回同一字母序）；但 **HTML 版 `/collections/all?sort_by=best-selling`
  生效**——与 `created-descending` 的前 20 名 0/20 重合

约束延续仓库既有事实：ECS 4C8G + RDS 2C4G、`max_connections=400`、无容器编排、
`THREAD_POOL_LIMIT=32` 由导出/探活/bcrypt/同步后台任务共用。

## Goals / Non-Goals

**Goals:**

- 让独立站的新品上架、价格变化、店内销量名次三类数据可采集、可存储、可查询
- 采集完全在服务端完成，不依赖插件、浏览器、用户登录或运营的任何配合
- 把「上新」这块界面立起来，使后续的 Amazon 采集变更接入时不必重建
- 不引入任何新的基础设施组件

**Non-Goals:**

- **不含 Amazon 浏览器插件采集**（另立变更）。因此 Amazon 卖家行的状态与占位符保持现状
- **不做绝对销量**。数据源只有店内相对名次，不换算、不估算
- **不做跨店可比的指标**。名次是店内的，不同店的第 10 名不可比
- **不镜像商品图片**。只存主图 URL，`/products.json` 是公开端点，不必在库里存副本
- **不支持非 Shopify 的独立站**。表上预留 `platform` 列，但本变更只实现 Shopify；
  遇到非 Shopify 站点显式拒绝并说明，不静默降级
- **不做取关后的 GC**。issue #56 定过「取消关注后保留 7 天」，但那是按每天全量轮询的
  数据量写的；被动采集量小一到两个数量级，现在写 GC 是为不存在的问题写代码。
  **这一条必须在界面/文档里说明是本变更不做，不能默默略过**——否则它会变成一条既写在
  issue 里、又没人实现的悬空承诺

## Decisions

### 1. 独立站与 Amazon 卖家分开建模，但共用分组、权限与上新流

**分**：数据模型与采集层。`competitor_seller` 是 `(seller_id, site)` 复合主键，独立站
两样都没有；为它编造站点码（`DTC` 之类）会给 `site_registry` 这个唯一事实来源开出第二
个入口，正是 CLAUDE.md 反复警告的形态。字段也几乎不重叠：Amazon 有 BSR 与评价数没有
上架时间，独立站有上架时间与变体没有任何销量。采集更是一推一拉，issue #56 已写明
「两套接口形态要分开，不要强行统一」。

**合**：分组、权限点、上新流。P0 那条「分组不绑站点，只是标签」的决定在这里兑现——
同一分组可同时装两类成员，无需改动分组表。权限点沿用 `competitor:view`：
「能盯 Amazon 卖家但不能盯独立站」不是真实的授权需求。

*备选*：给独立站也塞进 `competitor_seller`，用域名当 `seller_id`、站点填 `DTC`。
省一张表，但代价是污染站点码事实来源，且 `(seller_id, site)` 的语义从此含糊。否决。

### 2. 三类数据分三张表，不用单宽表也不用每日全量快照

粒度与写入模式两两都不同：

```
店        17 行            抓取状态挂这里
商品      ~13,600 行       17 家店 × 平均 800 个商品，只增不改
变体      ~92,000 行       6.3 倍放大，价格挂这里
名次×天   1,700 行/天      只存前 100 名
```

单宽表只有两种塞法：按变体展开则商品属性重复 6.3 次（最坏 169 次）；变体塞 JSONB 则
「哪些商品降价了」变成对全表做 JSONB 展开加窗口函数。**这个仓库已经为第二种付过一次
学费**——V1 就是 `amazon_origin_search_data` 单宽表 + `ranking_trend_day` JSONB 存 7 天
走势，V2 整个重建成星型模型就是为了摆脱它。

价格若按每日全量快照存：

| | 年增行数（17 店） | 100 店时 |
|---|---|---|
| 每天每变体一行 | 3360 万 | 1.98 亿 |
| 变更日志 + 名次前 100 | **约 110 万** | 约 650 万 |

**30 倍差距，且其中约 99% 的行与前一日完全相同。** 这不只是空间——`dim_product` 那次
`IS DISTINCT FROM` 的教训是写入代价：PostgreSQL 的 UPDATE 无论新旧值是否相同都写新
元组、标死旧元组、并在每个索引上插新条目，同一份日报因此从 54 秒退化到 416 秒
（issue #33）。同一条纪律在这里就是「价格没变就不要写」。

价格与名次也不能互相合并：粒度一个是变体一个是商品，写入一个稀疏一个每日，覆盖一个
全量一个只有前 N。合成一张会让一半的列恒为 NULL，且读的人无法从表结构判断某天没有行
意味着「没变化」还是「没进前 100」。

**四张表 MUST NOT 登记进 `PARTITIONED_TABLES`**。登记即被保留清理按
`HOT_WINDOW_MONTHS=3` 整分区 DROP，而价格与名次的历史越长越值钱。那个三个月窗口是为
八亿行的 ABA 事实表定的，与本能力的量级无关。

### 3. 完整性标记是下架判定的唯一前提

拉取完整 = 每页都 200 + 翻页因空页自然终止 + 无重试耗尽。不完整时照常写入见到的商品
（只增，永远安全），但绝不判下架——一次网络抖动把整店判成清仓，是这条路唯一能造成
大面积假数据的方式，而 `lumerosy.com` 实测就偶发超时过一次。

**撞上页数上限必须记为不完整。** 上限设 `DTC_MAX_PAGES=40`（一万个商品），实测最大的
店 1241 个商品、5 页，离上限很远；但若某天有店真涨到一万个，把撞上限当正常结束会让
第 40 页之后的商品被安静地判成下架。

这与 Amazon 侧「只做并集、永不推断下架」形成对照：那边只能看到第 1 页 16 条，永远没有
完整性可言；这边拿的是全量目录，所以下架检测**是**可做的——前提是完整性被显式记录。

### 4. 新品判定看商品是否已在库，不看 `published_at`

商户批量重新发布会让 `published_at` 整体跳到当日，据此判定会伪造一批假上新。判据是
「这个 `product_id` 以前见过没有」。三个时间（`published_at` / `created_at` /
`first_seen_at`）都存，是为了出问题时能分辨。

由此得到一个 Amazon 侧没有的好处：**首刷即有历史**。第一次拉取把 `published_at` 原样
写入，当场就能回答「这家店近 7 天上了什么」，一条基线都不用建。

但**首刷那批不进上新流**——新纳入的站点上个月发的 250 个商品不是「今天上新」，只是我们
刚开始看。上新流按 `first_seen_at`，历史查询按 `published_at`，这正是两个时间都要存的
第二个理由。

### 5. 销量只能是店内相对名次

`/products.json` 无销量字段。实测排除的三条替代路径：

- **JSON 端点的 `sort_by`**：实测被忽略，`best-selling` / `created-descending` /
  `manual` 返回同一字母序。只有 HTML 版生效
- **库存递减法**：实测 `inventory_management: null`，该店压根没开库存跟踪，铺货站普遍如此
- **加购试探**（往购物车塞超量商品，从报错里读剩余库存）：对他人站点发写请求，不做
- **评价数**：依赖第三方评价 app（Judge.me / Loox / Yotpo），各家装的不同，取数逻辑要
  按 app 分别写，收益不抵复杂度

因此销量呈现为店内畅销榜名次 + 历史走势，界面文案不出现销量/销售额/绝对数量。
单日名次信息量有限，**变化才是信号**——某商品两周内从第 400 名升到第 12 名。

代价：这是本变更相对 Amazon 侧最弱的一环（那边有 BSR 这种全类目绝对排名）。两条路在
这一点上正好互补，这也是不能只做一条的原因。

### 6. 调度复用 `import_queue.py`，按状态列认领，`SKIP LOCKED` 而非全局咨询锁

那个循环已经在干两件同构的事（回收超时直传批次、清理过期竞对预览），加第三件即可。
「到点了没」由 `last_fetch_at` 状态列判定而非进程内计时器——后者在进程重启、多 worker
或崩溃后都会失效，而失效的表现是「再也不更新了」，与 issue #56 里那个「批次永远排队」
是同一种病。

认领用行级 `FOR UPDATE SKIP LOCKED LIMIT 1`，每轮一站，抓完立刻再来一轮
（照搬导入接手的 `continue`），17 家店约 2~3 分钟走完一遍。

**不用全局咨询锁。** 导入串行化是因为两个 GB 级导入会争抢 WAL 与索引构建；本能力一次
写入几千行、瓶颈在网络，全局串行化只会让站点数增长时排队时间线性膨胀。

### 7. 网络走 async httpx，只有数据库写入进线程池

`httpx` 已在依赖里（`dingtalk_client.py` 用的就是 `AsyncClient`），无新增依赖。

**不要照抄旁边 `run_in_threadpool(drain_import_queue, ...)` 的写法把整个抓取塞进线程。**
那 32 条线程由 bcrypt 登录（每次约 247ms）、CSV 导出、健康检查探活与同步后台导入共用；
一家店抓 8 秒就占住一条线程 8 秒，站点数涨上去会实实在在地拖慢登录。导入走线程池是
因为它同步阻塞，本能力不是。

### 8. 解析器是纯函数，与 `seller_ref_parser.py` 同一模式

`store_fetcher.py` 输入响应文本、输出结构化数据，不连库不连网。单测用固定样本
（一份 `/products.json` 响应、一份畅销榜 HTML）。**测试不得访问真实站点**——外部站点会
变化、会失败，据此写的测试既不稳定也无法归因。

畅销榜是本变更唯一的 HTML 依赖。提取靠 `/products/{handle}` 链接的出现顺序，不依赖
class 名（实测有效），比 Amazon 那边稳；但主题不同仍可能影响，所以要有独立的
`rank_ok` 状态——**取到页面却提取出 0 个商品，是解析器坏了，不是「这店没商品」**。

## Risks / Trade-offs

- **[覆盖面小：17 个独立站 vs 2667 个 Amazon 卖家]** → 接受。这条路不是 Amazon 那条的
  替代，是一条更便宜、无前置依赖的独立路径。但值得向运营确认一件事：书签里只有 17 个
  独立站，是因为只关心 Amazon 卖家，还是因为独立站没有好办法收藏所以没攒？若是后者，
  真实关注面可能大得多，而「粘贴域名即可盯上新」会把攒的成本降到接近零。

- **[畅销榜依赖 HTML 结构，主题变化会失效]** → 用链接顺序而非 class 名提取；
  `rank_ok` 独立成状态并在界面明示；目录与名次的成功标记互不牵连，名次挂了不影响
  新品与价格两项。

- **[`/products.json` 可被商户关闭]** → 单独一种状态「该站点未开放商品接口」，与
  「抓取失败」区分展示。这 17 家目前都开着，但这是商户可改的。

- **[界面先围着 Shopify 的丰富字段设计，Amazon 接入时塞不下]** → 上新流主列表只用两类
  来源的交集字段（店铺/卖家、商品、时间、来源），各自独有的进详情。这条在 spec 里是
  硬要求，不是建议。

- **[名次是 Shopify 自算的口径，我们无从校验]** → 接受。它是相对信号不是绝对数字，
  界面文案已约束为「店内畅销榜名次」。用它看趋势而非看绝对值，本身就不依赖口径精确。

- **[`published_at` 语义可能因商户操作而漂移]** → 新品判定不看它（决策 4），
  三个时间都存以便事后分辨。

- **[单个站点商品数远超预期]** → `DTC_MAX_PAGES` 兜底，撞上即判不完整、不判下架，
  并记录可排查的错误。不会静默丢数据。

- **[非 Shopify 的独立站]** → 显式拒绝并说明原因，不静默降级。`platform` 列预留，
  接第二种建站平台时是加法。

## Migration Plan

1. 一条 Alembic 迁移建四张普通表，全部登记进 `migration_scope.py` 的 `V2_TABLES`
   （漏登的表 autogenerate 既看不见也不报错，`test_conventions.py` 会拦）。
   **MUST NOT** 登记进 `PARTITIONED_TABLES`。用 `alembic upgrade head --sql` 核对生成
   的 DDL 里没有 `PARTITION BY`（普通表符合预期）。
2. `alembic upgrade head` 后表为空，无 backfill。
3. 后端上线：新端点，不影响既有端点；轮询循环新增一件事，站点表为空时该分支直接跳过，
   对现有部署无行为改变。
4. 前端上线：竞对监控页新增分段。
5. 首批站点由用户手工粘贴域名录入；首次拉取即写入历史，不需要等待周期。
6. **回滚**：`alembic downgrade -1` 删四张表；前后端各自回退上一版本。无数据损失风险
   ——本变更不写 `fact_*` / `dim_*`，也不修改 P0 的任何既有表结构（分组表复用但不改
   schema）。

按 V2 的既有约定，本变更不单独发布，随 V2 整体上线。

## Open Questions

- **运营对独立站的真实关注面有多大**（见 Risks 第一条）。这不阻塞实现——17 家和 200 家
  的代码是同一份，抓取成本从 136 次/天涨到 1600 次/天仍然微不足道。但它影响这条路在
  路线图上的权重，值得在实现期间问一句。
- **`de.molooco.com` 的证书异常**是该站自身的问题还是子域证书配置，实现时按普通的
  「抓取失败」处理即可，不必为单站特例开分支。
