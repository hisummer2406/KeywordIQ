## ADDED Requirements

### Requirement: 多进程日志写入不因轮转丢失或损坏

应用以多个 worker 进程共享同一个物理日志文件时，轮转（按天）SHALL NOT 导致任何进程的
写入丢失、被覆盖，或在新文件中出现空洞字节。应用进程自身 MUST NOT 各自独立判断"是否
该轮转"并执行 rename——轮转的权威 SHALL 是应用进程之外的单一机制（操作系统级
`logrotate`），应用侧只负责在检测到当前打开的文件已被替换时重新打开。

#### Scenario: 4 个 worker 并发写入且触发一次轮转

- **WHEN** 4 个独立进程同时向同一个日志文件写入带唯一标识的记录，期间该文件被外部
  轮转机制 rename 为归档文件并重新创建同名空文件
- **THEN** 轮转前写入的全部记录完整出现在归档文件中，轮转后写入的全部记录完整出现在
  新文件中，两者之间没有记录丢失、重复或写入了错误的文件

#### Scenario: 轮转后新写入自动进入新文件

- **WHEN** 日志文件被外部机制以 rename+新建同名文件的方式轮转
- **THEN** 应用进程的下一次日志写入 SHALL 落在新创建的文件里，不需要重启进程

### Requirement: 每个请求产生可检索且跨层关联的摘要记录

每个 HTTP 请求结束时，系统 SHALL 记录一条摘要，至少包含：HTTP 方法、请求路径
（MUST NOT 含 query string）、响应状态码、总耗时、以及贯穿该请求的 request id。
健康检查端点（`/health`）不计入该摘要。

摘要 SHALL 区分请求的结束形态：正常完整发送响应、响应头已发出但响应体未完整发送即
中断（客户端断连或任务取消，且过程中没有异常抛出）、响应头发出后抛出未处理异常。
后两种 MUST NOT 与"正常完成"混同记录。

跨代理层（nginx）与应用之间 SHALL 使用同一个 request id，使得一次请求可以在两层
日志中被同一个编号检索到；代理层未能连接到应用（如 502/504）时，代理层的日志记录
SHALL 仍然携带一个可检索的编号，即使应用侧没有产生对应记录。

#### Scenario: 成功请求产生摘要

- **WHEN** 一个请求正常处理完成并返回 2xx
- **THEN** 日志中出现一条该请求的摘要记录，结束形态为"正常完成"，且不含请求的
  query string

#### Scenario: 业务失败与未捕获异常均产生摘要

- **WHEN** 一个请求因业务规则被拒绝（如非法作用域）或触发未捕获异常
- **THEN** 日志中出现一条该请求的摘要记录，状态码与实际返回一致

#### Scenario: 流式导出中途断连不被记为正常完成

- **WHEN** 客户端在流式导出响应发送过程中断开连接，且发送过程本身没有抛出异常
- **THEN** 该请求的摘要记录的结束形态 MUST NOT 是"正常完成"，SHALL 标识为中途中断

#### Scenario: 健康检查不产生摘要噪音

- **WHEN** 健康检查探活请求（`GET /health`）被处理
- **THEN** 该请求 MUST NOT 产生请求摘要记录

#### Scenario: 通过 request id 跨层关联一次慢请求

- **WHEN** 维护者拿到一次请求在响应头或错误响应体中的 request id
- **THEN** 使用该 id 分别检索代理层访问日志与应用日志，两侧都能找到与这次请求对应的
  记录

#### Scenario: 代理层连接失败时仍有可检索编号

- **WHEN** 代理层无法从应用获得响应（如上游超时或拒绝连接）
- **THEN** 代理层的日志记录中仍包含一个该请求的编号，即使应用侧因未收到请求而没有
  对应记录

### Requirement: 慢查询定位覆盖全部数据库执行路径

系统的慢查询检测 SHALL 覆盖应用实际使用的每一种数据库执行路径（同步与异步引擎），
不得只覆盖其中一种而让另一种查询路径的慢查询完全不可见。检测阈值 SHALL 是可配置项，
不得硬编码在无法通过配置调整的位置。

#### Scenario: 异步查询路径的慢查询被记录

- **WHEN** 一条通过异步数据库引擎执行的 SQL 语句耗时超过配置阈值
- **THEN** 该语句被记录为慢查询，记录中包含语句文本但不包含参数值

#### Scenario: 阈值可通过配置调整

- **WHEN** 运维调整慢查询判定阈值的配置项
- **THEN** 判定行为按新阈值生效，不需要修改代码

### Requirement: 分析查询屏慢请求提供结构化诊断且不新增查询

`POST /api/analysis/search` 的单次调用总耗时超过可配置阈值时，系统 SHALL 输出一条
结构化诊断记录，内容包括：该次请求实际解析生效的作用域（站点、视图、锚定日期——
SHALL 是实际执行时使用的值，不是请求中的草稿参数）、分页与排序参数、筛选维度的
白名单摘要、以及该次调用内部各主要执行阶段的耗时。总耗时低于阈值时 MUST NOT 输出
该诊断记录。产出该诊断记录的过程 MUST NOT 对数据库发起在正常处理流程之外的额外查询
（如为诊断专门发起的 COUNT 或探测查询）。

筛选维度的白名单摘要 MUST NOT 包含检索词、ASIN 或其他用户输入的原始文本值，只能是
预先约定的布尔或计数字段。

无法测量为独立耗时的部分（如数据库连接获取与 SQL 执行本身在现有实现下是合并测量的）
SHALL 在字段命名或说明中明确标注为未细分，不得以整体耗时冒充某个更细粒度阶段
（如不得把应用层整形/序列化耗时算作数据库执行耗时）。

#### Scenario: 超过阈值输出真实生效条件与阶段耗时

- **WHEN** 一次 `/api/analysis/search` 调用总耗时超过配置阈值
- **THEN** 日志中出现该次调用的诊断记录，其中的作用域字段与本次响应实际返回的数据
  所对应的作用域一致，且包含各主要执行阶段的耗时字段与总耗时

#### Scenario: 低于阈值不输出诊断

- **WHEN** 一次 `/api/analysis/search` 调用总耗时未超过配置阈值
- **THEN** 不产生该结构化诊断记录

#### Scenario: 诊断记录不泄漏检索词

- **WHEN** 一次触发诊断记录的请求携带了检索词或 ASIN 筛选
- **THEN** 诊断记录中不包含该检索词或 ASIN 的原始文本，只包含预先约定的白名单字段
