## Context

- 现状：运营每天从卖家后台「品牌分析 → 热门搜索词」下载 US/GB/DE 的日报（约 6～7 万到 50 万行，230MB 级）和周报（US 约 286 万行，GB 级），在后台页面经 STS 直传 OSS，回传 object key 后由 `run_import` 三段式导入（COPY 暂存 → 维度 → 事实），导入受咨询锁串行，排队由 `main.py` 的「导入队列」轮询接手。
- CSV 固定 21 列、按位置映射（`app/table/upload/importer.py` 头注释）：排名、搜索词、品牌 #1～3、类目 #1～3、三组（ASIN、标题、点击份额、转化份额）、报告日期。品牌、类目是**关键词级**按点击排出的名次，不是三个 ASIN 的属性（同一 ASIN 槽位 1 的品牌冲突率 11.7%，见 importer 内实测注释）。
- 这些列被下游大量使用：`fact_*` 的 `top1～3_brand_id` / `top1～3_category_id`、`dim_brand` / `dim_category`、`keyword_brand_hit`、`brand_stats`、市场分析的品牌/类目筛选与「排除词里含品牌」。
- 期次日期口径：日报为报表当天；周报为周六结束日（如 `Week_2026_11_07`，2026-11-07 是周六）。
- 生产为单台 4C8G ECS，PG 与应用同机；导入期间与交互查询抢 CPU 和磁盘（2026-11-10 #201 实测 936 秒，其中商品维度写入单条 672 秒）。

## Goals / Non-Goals

**Goals:**
- 日报、周报无人值守获取，缺期可被发现，人工上传保留并可随时兜底。
- 自动获取的产物与人工上传走同一条导入管线和同一套校验、归档与重导机制。
- 在实现前用真实样本选定路线，避免把数据口径变化悄悄带进分析结果。

**Non-Goals:**
- 不同时实现两条路线；未选中的路线只保留在本文作为备选。
- 不改导入内核的性能（商品维度写入慢另立项）。
- 不接入 SP-API 的其他报表（搜索查询表现、目录、广告等）。
- 不回填历史期次；自动获取只从启用日起向后补齐，最多回看一个配置窗口。

## Decisions

### 决策 1：先设路线选定闸门，再写实现

两条路线的差异集中在数据口径，无法靠文档推断定案：SP-API 公开文档未列出品牌、类目字段，日数据还可能延迟；行数覆盖（文档称约 1200 万条上限）与卖家后台 CSV 是否一致也未知。所以 tasks 第 1 组是「拿权限 → 拉样本 → 与同期人工 CSV 对账 → 把结论写回本节」，在这之前只做两条路线共用的部分（来源字段、去重、缺期告警），调度开关默认关闭。

替代方案：直接选 SP-API。否决理由：品牌/类目缺失会让 API 期次的品牌筛选、品牌统计静默变空，违反「缺失、未知与真 0 分开」，而且一旦上线混入历史就难以区分。

### 决策 2：两条路线的对比

| 维度 | 路线 A：SP-API 报表 | 路线 B：插件自动下载 CSV |
|---|---|---|
| 数据与人工一致性 | 不一致：缺品牌、类目、标题；行数覆盖待对账 | 完全一致，同一份文件 |
| 运行位置 | 服务端（app 轮询 job），无需人值守 | 运营电脑上的 Chrome，须常开且保持卖家后台登录 |
| 前置条件 | 品牌备案 + SP-API 开发者注册 + 品牌分析角色审批（周期与结果不可控） | 已有插件和令牌同步机制；需新增卖家后台 host 权限 |
| 后端改动 | 大：LWA 鉴权、报表生命周期、GB 级 gzip JSON 流式转换、品牌/类目「来源未提供」口径 | 小：复用 `upload-credentials` + `oss/import`，只加来源字段 |
| 脆弱点 | 接口限流、报表 FATAL/CANCELLED、日数据延迟 | 卖家后台改版、会话过期、电脑休眠或断网（11-10 的 #200 即此类） |
| 合规 | 官方接口 | 自动操作卖家后台页面，需确认符合亚马逊使用条款 |
| 失败时兜底 | 人工上传 | 人工上传 |

倾向：若对账显示 SP-API 能提供品牌/类目或等价字段，选 A；否则选 B，A 留作后续在补齐字段后再评估。最终以闸门结论为准。

### 决策 3：共用部分——来源字段与去重

- `analysis.import_batch` 新增 `source VARCHAR(16) NOT NULL DEFAULT 'MANUAL'`，取值 `MANUAL` / `EXTENSION` / `SPAPI`，加 CHECK 约束。Alembic 迁移只加列和约束（`ADD COLUMN ... DEFAULT` 在 PG 15 对常量默认值是元数据操作，不重写表；该表约 200 行，无锁风险）。不动 `analysis` 下的分区表和事实表。
- 去重判定放在 service 层的一个函数里，人工凭证签发不调用它（人工上传行为不变），自动路径调用：同站点 × 周期 × 期次存在 UPLOADING/QUEUED/PROCESSING/COMPLETED 即跳过。查询走现有索引 `idx_import_batch_site_period (site, period_type, report_date)`，不新增索引。
- 失败重导继承原批次 `source`。

### 决策 4：路线 A 的实现要点（仅在选中时实施）

- **调度位置**：作为「导入队列」轮询里**最后一个** job（低于排队接手和独立站刷新），每轮最多推进一个期次的一个状态步：请求报表 → 查询状态 → 下载文档 → 转换上传 → 登记批次。报表生成要几分钟到几十分钟，按状态步推进，不在单轮里阻塞等待。报表 ID 与状态持久化在新表 `analysis.spapi_report_request`（同一迁移创建），轮询重启后可续。
- **单点执行**：轮询在每个 worker 里都跑，job 内用独立咨询锁（新 key，不与导入锁 19273 共用）保证同时只有一个 worker 推进。
- **阻塞工作不进事件循环**：HTTP 下载与 JSON 转换用 `asyncio.to_thread`，下载流式写临时文件，不整读进内存。
- **格式转换**：报表是 gzip JSON，结构为每个（部门，搜索词，被点击 ASIN）一条记录，按 `clickShareRank` 排出前三。转换器流式读取（引入 `ijson`），先按长表写成中间 CSV，再在 SQL 侧透视为现有 21 列布局的暂存行，这样不依赖源记录排序、内存有界。缺失的品牌、类目、标题列写空。
- **「来源未提供」口径**：`SPAPI` 批次对应期次的品牌/类目为「不可得」，不是「无品牌」。需要在查询侧按批次来源区分并在界面提示，这会改变市场分析的可见行为，届时补 `site-scoped-query` 等 delta 并跑 `verify-analysis-contract`。标题缺失时不覆盖 `dim_product.title`（现有 `IS DISTINCT FROM` 更新会把标题改成空串，转换路径必须跳过空标题）。
- **限流与重试**：遵守 Reports API 的速率限制；FATAL/CANCELLED 记录原因并在下一轮按退避重试，次数达到上限再交给缺期告警。
- **配置**：`SPAPI_ENABLED`（默认 false）、LWA client id/secret/refresh token、各站点 marketplace id 与区域端点、截止时间、回看窗口。凭证只在 ECS `.env`。

### 决策 5：路线 B 的实现要点（仅在选中时实施）

- 插件新增后台模块：用 `chrome.alarms` 定时，打开卖家后台热门搜索词页面，按站点和周期选择期次、触发下载，拿到文件后走与网页相同的「换凭证 → 直传 OSS → 回传 object key」流程，凭证请求带上 `source=EXTENSION`。
- 后端只扩展 `upload-credentials` 接受 `source`（白名单校验，默认 MANUAL），并在签发前调用决策 3 的去重；插件也先调一个只读接口查询应到但缺失的期次，避免下载已有的文件。
- 直传沿用前端现有的分片、续签、断点续传与放弃时回收分片逻辑（`frontend/src/services/ossUpload.ts`），抽成插件可复用的实现或在插件内按同样语义实现。
- 卖家后台的下载流程（是否异步生成、下载管理器位置、文件命名）须在闸门阶段实地确认，再定插件的页面交互方案。

### 决策 6：缺期告警放在运维机器人

ops_bot 已有定时任务框架和导入完成/失败通知。新增一个检查：对已启用的站点 × 周期，截止时间后查询期次是否有 COMPLETED 批次，按期次去重告警、补齐后发恢复。ops_bot 不 import 业务 app，只读 `analysis.import_batch`；告警状态存 ops schema 新表并登记 `OPS_TABLES`。

### 对资源的影响

- **连接池**：共用部分只多一次小表查询。路线 A 的 job 每轮至多占一个异步连接做状态读写，下载与转换期间不持有连接；导入本身仍走同步池，无新增占用。路线 B 无新增。
- **内存**：路线 A 下载落临时文件、流式转换，内存与文件大小无关；临时文件磁盘占用与周报同量级（GB 级），转换上传后立即删除，磁盘告警阈值已有（70%/90%）。
- **索引与执行计划**：不新增索引，去重查询命中现有 `idx_import_batch_site_period`；导入 SQL 与查询 SQL 不变（路线 A 的品牌口径若改查询，届时另行评估）。

## Risks / Trade-offs

- [SP-API 品牌分析角色审批不通过或久拖] → 闸门前只做共用部分，路线 B 作为现成备选；人工上传始终可用。
- [路线 A 品牌/类目缺失导致分析口径混杂] → 来源字段区分，查询侧显式标注「来源未提供」；对账结论未写入前不开启调度。
- [路线 B 依赖运营电脑在线] → 缺期告警兜底；文档写明电脑需常开、禁用休眠。
- [卖家后台改版或条款风险（路线 B）] → 闸门阶段确认条款；插件失败只影响自动获取，不影响人工上传。
- [自动与人工同时上传同一期次] → 自动路径签发前去重；人工路径不拦，最坏情况是重复导入同一期次，与现状一致（导入是追加，同期次重导口径另由现有规则约束）。
- [日数据延迟导致误判缺期] → 「数据源尚未产出」记待重试，截止时间按站点可配，首轮取保守值后按实测调整。

## Migration Plan

1. 合并共用部分（来源字段迁移、去重函数、缺期检查但开关关闭），按现有 `Deploy V2 to ECS` 发布；迁移只加列，回滚为删列。
2. 闸门：拿到 SP-API 权限后在本机拉三站点日、周样本各一份，与同期人工 CSV 对账，结论写回决策 2，选定路线。
3. 实现选中路线，开关默认关闭；先在一个站点、一个周期试运行一周，期间人工照常上传，对比自动批次与人工批次。
4. 试运行通过后逐站点开启，人工上传降为兜底。
- 回滚：关闭开关即停止自动获取，已导入的批次照常可用；来源列保留无害。

## Open Questions

- SP-API 搜索词报表是否真的不含品牌、类目（以拿到权限后的真实样本为准）？行数覆盖与卖家后台 CSV 差多少？
- 日数据通常延迟多久产出？截止时间设在北京时间几点合适？
- 卖家后台自动下载是否符合亚马逊使用条款？运营是否有一台可常开的电脑？
- 启用后人工是否完全停止上传，还是保留周报人工？（影响去重与告警口径）
