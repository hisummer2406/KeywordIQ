## Context

`preserve-analysis-screen-state`（2026-08-16 归档）解决了「切走再切回丢状态 + 重发 4 个
请求」这个真问题，但顺带做了一件需求方没要的事：把分析查询屏的首屏查询改成手动触发。
需求方要的是**增长屏**延迟查询，分析屏应当进去就有数据。

两屏当前的实现正好互换：

| | 分析查询屏 | 持续增长市场屏 |
|---|---|---|
| 挂载 effect | `reloadScopeMeta(...)`，**不** apply | `reloadScope().then(s => apply(...))` |
| 结果 | 表格留空等点击 | 立即查一次 |

约束是这次改动**只动前端两屏的挂载行为**：后端两个 `/search` 端点的契约、参数、权限点
一律不动，连接池占用、内存与执行计划都不受影响（请求次数的变化在两屏之间互相抵消，
净变化为零）。**无数据库改动，无 Alembic 迁移。**

## Goals / Non-Goals

**Goals:**

- 分析屏首次进入（无会话缓存）时按默认作用域自动查询一次。
- 增长屏改为延迟查询，并补齐「还没查 ≠ 0 行」的三处界面配套。
- 把已归档规格里那条按错屏的要求撤掉，并给增长屏补上它本就缺的首屏规格。

**Non-Goals:**

- **不给增长屏加会话缓存。** 它今天切走再切回仍会丢条件并重发 3 个请求。那是
  `preserve-analysis-screen-state` 归档 design 里已列明的 out of scope。混进本变更会让
  评审无法分别判断两件事，且延迟查询本身会**放大**那个缺陷（切回来不但丢条件，还得
  重新点一次查询）——这一点写进 Risks，不在这里顺手修。
- 不动排序、分页、筛选等任何已生效的交互。
- 不动两个后端端点。

## Decisions

### 决策 1：分析屏的自动查询接在 `reloadScopeMeta` 的 `.then` 上，不另起一个 effect

`reloadScopeMeta` 已经负责解析默认作用域（默认站点、最新日期）并返回解析结果 `s`，
`apply` 需要的正是这份结果。接在它的 `.then` 上，「拿到作用域」与「用它查一次」在代码里
是同一条链，读得出因果。

**否决的替代**：起第二个 effect 监听 `scope` 变化后自动查。那会让**每次改站点/视图**都
自动查（`reloadScopeMeta` 在那些路径上也会跑），直接推翻「查询由显式动作触发」这条
既有约定——而那条约定与本次改动无关，不该被顺带改掉。

### 决策 2：`restored` 短路留在最前面，自动查询在它之后

挂载 effect 现在的第一行是 `if (restored) return;`。自动查询写在这行之后，天然继承
「有缓存就整段跳过」的语义，切回来一个请求都不发这条已验证的行为不受影响。

顺序反过来（先 apply 再判断缓存）会让每次切回都多查一次，正是上一个变更刚修掉的病。

### 决策 3：`hasQueried` 这个判据在两屏走向相反，但机制同一份

- **分析屏**：自动查询之后 `appliedSig` 立刻非空，`hasQueried` 恒真，它作为「还没查」的
  判据就失效了。但它还管着「有未生效改动」标签的显隐（首屏那一刻草稿与生效相同，标签
  本就不该出现），所以**保留变量、换掉空状态的判据**：空状态改看**有没有可查日期**。
- **增长屏**：反过来，`hasQueried` 从无到有，同时承担空状态文案、条数显隐、dirty 标签
  三处判据——与分析屏改造前一模一样。

**为什么分析屏的空状态判据是「有无可查日期」而不是「查询是否返回过」**：表格 `request`
开头有 `if (!body?.date) return {data:[], total:0, success:true}` 这道守卫，站点没有数据时
它压根不发请求。此时「查询返回过」为真但一次网络请求都没有，用这个判据会显示
「搜索结果：0」，把「这个站点没导过数据」说成「条件筛出来是 0 行」。

### 决策 4：增长屏不复制分析屏的 `stateCache`，只复制那三处界面配套

三处配套（条数显隐、dirty 标签前置、空状态文案）是**延迟查询自带的义务**——不做，
「还没查」就会伪装成「今天没有增长词」，而这一屏的空结果本来就有两种正当成因（缺期、
口径过严），再混进第三种「还没查」，用户没有任何办法分辨。

缓存则是另一个问题的解法，不是延迟查询的义务，故不带。

### 决策 5：测试改造走「反转已有用例」而不是「新写一组」

两屏的首屏行为在测试里都已有覆盖，方向反了而已。分析屏 `index.test.tsx` 的
`renderSettled(expandFilters, query)` 默认会替测试点一次「立即查询」——自动查询之后这个
默认动作是多余的一次点击，会让「首屏是否自动查」的用例永远为真、测不出回归。所以
`renderSettled` 的默认值要跟着改，改完必须确认那 25 个依赖它的用例仍然绿。

## Risks / Trade-offs

- **[增长屏延迟查询会放大它自己的「切走再切回」缺陷]** → 切回来不只丢站点/日期，还要
  用户重新点一次查询。已知且接受：那一屏是低频工具屏，且修法是给它加会话缓存，属于
  独立变更。写进 Open Questions，不在本次做。
- **[分析屏自动查询在慢查询下拖长首屏]** → 默认作用域是「默认站点 + 按天 + 最新一期 +
  无筛选」，无筛选路径的总数直接读 `site_data_stats`（O(1)），是这一屏最便宜的一种查询；
  周报那条最坏近 1 秒的路径要用户手动切到按周才会走到。风险可接受。
- **[`renderSettled` 默认值一改，25 个无关用例跟着变]** → 它们本就应该在「有数据」的
  前提下跑，自动查询之后那个前提由首屏自己提供。改完全量跑一次前端测试确认。
- **[已归档规格被改写]** → `analysis-screen-layout` 少一条、改两条。REMOVED 块必须写清
  Reason 与 Migration，否则后人看到「首屏不查」被删会以为是遗漏。特别注意原要求里
  「缓存只存活于当前页面会话，刷新即失效」一句与首屏无关，**必须并入缓存那条要求**，
  不能随整条移除而丢失——这是 MODIFIED/REMOVED 最容易掉细节的地方。

## Migration Plan

纯前端行为改动，无数据迁移、无 Alembic 迁移、无接口变更，随 SPA 构建产物一同发布
（`./deploy.sh --skip-migrate` 即可）。回滚即回滚该次前端产物。

## Open Questions

- 增长屏要不要也上会话缓存（切走再切回保留站点/日期/结果）？延迟查询让这个缺陷更疼，
  但它是独立的一件事。留待需求方按实际使用频率决定。
