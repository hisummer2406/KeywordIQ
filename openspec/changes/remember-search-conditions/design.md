## Context

分析查询屏的条件初始化今天只有两级：**会话快照**（`stateCache.ts`，模块级内存，刷新即
失效，切走再切回原样复原且零请求）与**内置默认**（`filters.ts` 的 `defaultFilters()`，
`isNew: true`）。挂载 effect 里那道 `if (restored) return;` 是两级之间的闸。

本变更在中间插入第三级：**用户保存的条件**。三者的存活期完全不同，这决定了它们各自存哪：

| | 存活期 | 存在哪 | 谁清它 |
|---|---|---|---|
| 会话快照 | 一次页面会话，刷新即失效 | 模块级内存 | `doLogout` / 刷新 |
| 保存的条件 | 跨登录、跨浏览器会话，直到用户主动删 | `localStorage` | 只有「重置条件」 |
| 内置默认 | 永久 | 代码 | —— |

约束来自三条既有约定：**（1）** 快照那条路「有快照就整段跳过初始化、一个请求都不发」，
本变更不得穿透它；**（2）** 「一个筛选维度恰好一个入口」，排除了再加一个「恢复我的条件」
按钮；**（3）** 站点码非法时后端**报错不回退**（`DEFAULT_SITE` 只用于未传站点），所以
失效站点必须由前端自己兜。

## Goals / Non-Goals

**Goals:**

- 用户存一次，之后每次登录进屏就是他那组条件，不必每天重调。
- 保存的条件与界面控件、与实际发出的请求三者一致——不出现「表格是德国站、控件显示美国站」。
- 「保存了没有」「现在用的是不是我保存的那组」在界面上可读。
- 保存的数据在形状变化、站点下线、换账号这三种情况下都不会把用户带进一个坏状态。

**Non-Goals:**

- 不跨设备同步（决策 1 的自觉代价）。
- 不做多份具名方案、不做「历史记录」列表（那是 issue #37 的第 2 项，独立变更）。
- 不改会话快照的优先级与实现。
- 不给增长市场屏加同样能力。

## Decisions

### 决策 1：存 `localStorage`，不建表

**代价说清楚**：换浏览器、换机器、清缓存即丢，且丢得**静默**——用户只会觉得「这功能
时灵时不灵」。接受这个代价换取零后端改动（无表、无迁移、无端点、无权限点）。

**替代方案（未采纳）**：建 `user_saved_query`（`user_id` 唯一 + JSONB + `updated_at`）
配三个瘦端点。跟着账号走，换机器不丢。前端工作量两条路**完全相同**，服务端只多一层薄的。
之所以没选：本次要先验证这个功能有人用；真有人用且抱怨「换台电脑就没了」时再搬，届时
`savedMode.ts` 的读写接口原样保留、只换实现。

### 决策 2：按 `currentUser.id` 分键，且跳过 `doLogout` 的清理

键形如 `keywordiq.analysis.savedMode.v1.<userId>`。

`doLogout` 现在 `clearSnapshot()` 清会话快照，理由是「同一标签页内换账号登录，绝不能
看到上一个用户的查询条件与结果行」。保存的条件面对同一个风险，但**解法不同**：会话快照
是单份无主的，只能靠清；保存的条件带用户 id，B 登录时读的是 B 的键，A 的那份自然看不见。

**所以保存的条件必须活过登出——这不是疏漏，是需求本身**：清了它，「下次登录还是这组」
就不成立了。`doLogout` 里要留一条注释写明两者待遇不同的理由，否则下一个人看到「登出清
一半」会顺手补全。

取不到 `currentUser.id` 时（初始状态还没取回、或取回失败）**视同没保存过**，既不读也不
写——绝不回退到某个无主的共享键，那正是串账号的入口。

### 决策 3：payload 自带 `version`，对不上就静默丢弃

`localStorage` 里这份能活几个月、跨好几次上线，而 `FilterDraft` 的形状会随功能演进。
读取时校验 `version`，不等于当前值就当作没保存过（并顺手删掉那条）。

**不做形状迁移**：写一套把 v1 payload 升到 v2 的代码，需要为每个历史形状保留一份转换器，
而收益只是省用户一次「重新保存」。丢弃 + 让用户重存一次，成本对用户是 10 秒。

这条比会话快照那边的 `CACHE_VERSION` 更要紧：快照最多活一次刷新，而这份能跨月。旧形状
渗进 UI 的表现是零散的空白控件，极难归因——`CACHE_VERSION` 的注释记的就是这个教训。

### 决策 4：保存的是**生效条件**，不是草稿

按钮读 `appliedRef.current`（与导出同源）。草稿改了没点「立即查询」就保存，等于存下一组
用户自己都没见过结果的条件，下次登录进屏看到的东西他不认识。

`appliedRef.current` 为空（作用域无可查日期，一次都没查成）时按钮**不可用**，而不是存一份
空条件。

### 决策 5：站点失效时乐观回退，那次调用 `skipErrorHandler`

首屏直接拿保存的站点发 `/scope`。站点已从 `ENABLED_SITES` 移除时后端报错（不回退是既有
约定），前端捕获后：回退到默认站点重新解析、**删掉失效的保存项**、界面明示「你保存的
站点已下线，已切回默认站点」。

这次调用必须 `skipErrorHandler: true`。全局错误处理是「错误提示的唯一出口」，不跳过的话
用户会同时看到一个红色报错和一句「已自动回退」，自相矛盾。**跳过之后必须自行呈现**——
静默回退比报错更糟：用户以为在看自己保存的站点，实际在看另一个。

**替代方案（未采纳）**：先 `getSites()` 校验站点再发 `/scope`。没有错误处理的麻烦，但把
首屏两个并行请求变成串行，多一个往返。站点下线是罕见事件，不值得让每次进屏都变慢。

### 决策 6：「重置条件」连带删除保存项，不做二次确认

「保存」与「重置」在同一行构成一对（存默认 / 回默认），重置自然应当把「我的默认」一并
撤掉，否则用户重置完、下次登录又回到那组他刚刚明确不要的条件。

**不做二次确认**（需求方明确要求）。**已知代价**：删除不可撤销，而「重置条件」看起来像
个只改表单的按钮，用户点它很随手；调了一上午的条件可能被一次误点抹掉，没有找回途径。
带「撤销」的提示条是不打断操作的折中，本次**不做**，留作后续独立调整。

重置**只动过滤区的筛选**，不改站点/视图/排序——它长在过滤区里，去改作用域栏的东西很
意外。所以重置后界面上站点仍是保存过的那个，但存储里那条已经没了。

### 决策 7：`savedMode.ts` 独立成模块，纯函数

读/写/清/版本校验都在这里，不散在组件里。理由与 `filters.ts` 相同：这是整块改动里唯一
有分支逻辑的部分（版本校验、用户 id 缺失、JSON 解析失败、站点失效清理），做成纯函数好让
它能被直接测，不用挂 DOM。

`localStorage` 本身也要防御：隐私模式下 `setItem` 会抛异常。写失败时不能让整屏崩——
捕获后提示「保存失败」，其余功能照常。

## Risks / Trade-offs

- **[换机器/清缓存后保存的条件静默消失]** → 决策 1 的自觉代价。缓解：界面上「我的默认」
  标记的有无就是当前状态的直接反映，用户看得见它没了，而不是察觉不到。

- **[保存的类目在该站点该视图下已不存在，筛出 0 行]** → 类目随导入变化，保存的类目可能
  在新期次里没有了。此时查询正常返回 0 行、界面照常显示「搜索结果：0」，不误导。
  **不在本变更内做类目有效性校验**——那需要把 `/categories` 的结果与保存项对账，属于
  另一个问题；且 0 行是可自解释的状态（用户看得到自己勾着哪些类目）。

- **[「重置条件」误删]** → 决策 6 已列明，不做确认也不做撤销，是需求方的明确选择。

- **[首屏请求从默认站点变成保存的站点，缓存命中率下降]** → 每个用户固定看自己那个站点，
  实际上比「所有人都先打默认站点再各自切走」更集中。不构成性能风险。

## Migration Plan

纯前端，无数据库迁移、无接口变更、无配置项。已有用户没有保存项，读到 `null` 即走内置
默认，与当前行为完全一致——**上线是无声的**，只有主动点过「保存当前模式」的人才会感到
变化。回滚即回滚该次提交；`localStorage` 里残留的键无害（没有代码读它），下次上线仍可用。

会话快照的 `CACHE_VERSION` **不需要 +1**：本变更不改快照的形状，只改「无快照时用什么
初始化」。
