# oss-first-ingestion Specification

## Purpose
表格文件的入口能力：文件先由前端凭受限临时凭证直传对象存储（OSS），字节不经应用服务器；
导入以该 OSS 对象为数据源流式装载，对象本身即原始归档，批次记录可据 object key 溯源与重导。

## Requirements

### Requirement: 表格文件先直传对象存储

上传 SHALL 采用前端直传对象存储（OSS）：后端 SHALL 签发受限的临时凭证（STS 或签名 URL），
前端凭该凭证把文件直接写入 OSS，文件字节 MUST NOT 经过应用服务器落盘。临时凭证 SHALL 限定
到本次上传所需的最小权限（指定 bucket、object key 前缀、写操作、短有效期）。上传完成后前端
SHALL 把 OSS object key 回传给后端以触发导入。

#### Scenario: 签发受限的直传凭证

- **WHEN** 前端请求上传一个日报文件
- **THEN** 后端返回一份临时凭证，其权限仅限于向约定的 bucket 与 object key 前缀写入，且有效期为短时

#### Scenario: 文件字节不经应用服务器

- **WHEN** 前端使用临时凭证上传一个约 1.5GB 的周报文件
- **THEN** 文件直接写入 OSS，应用服务器不落盘该文件、不承载其字节流

#### Scenario: 回传 object key 触发导入

- **WHEN** 前端完成直传并把 object key 回传给后端
- **THEN** 后端据该 key 登记一次导入，进入后续的从 OSS 拉取导入流程

### Requirement: 导入以 OSS 对象为数据源

导入 SHALL 以 OSS object 为唯一数据源：导入任务 SHALL 凭 object key 从 OSS 流式读取文件内容
并喂给数据库的 `COPY`，MUST NOT 要求先把整个文件下载并整体读入内存。若 object key 指向的对象
不存在或不可读，导入 SHALL 失败并给出明确错误，MUST NOT 写入部分数据。

#### Scenario: 从 OSS 流式导入

- **WHEN** 导入任务处理一个已直传到 OSS 的周报 object
- **THEN** 任务从 OSS 流式读取并通过 `COPY` 写入，导入过程内存占用有界

#### Scenario: 对象缺失时拒绝导入

- **WHEN** 触发导入时 object key 指向的对象在 OSS 中不存在
- **THEN** 该次导入失败并返回明确错误，不产生任何事实数据行

### Requirement: OSS 对象即原始归档

导入不再在应用服务器上做导入后归档：文件在入口处即已持久化于对象存储，OSS 对象本身
就是原始归档，可长期保留以供数据挖掘与 AI 训练重新处理。导入批次记录 SHALL 携带该对象
的 key/位置以供溯源与重导。

批次记录 SHALL 在**签发直传凭证时**创建，而不是等到导入被触发。object key 在签发那一刻
即已确定（凭证策略正是限死到该 key），因此记录自创建起就可溯源。落库失败时后端
MUST NOT 签发凭证——一份能用的凭证配一条不存在的记录，正是「文件传上去了、服务端不知道」
这一问题本身。

**「签发凭证」有两种，只有第一种落库。** 大文件的直传耗时可能超过凭证有效期，前端因此
会在传输途中反复**续签**凭证；续签的是同一次上传、同一个 object key，MUST NOT 因此新增
批次记录。后端 SHALL 能区分这两种调用：请求携带既有 object key 的即为续签，SHALL 只签发
凭证、MUST NOT 落库、MUST NOT 生成新的 object key。

续签请求携带的 object key SHALL 与导入触发、重导走同一套授权前缀校验，MUST NOT 因为
「这只是续签」而放宽——否则续签就成了绕过前缀限制、为任意 key 取得写凭证的入口。

导入触发接口 SHALL 认领该批次记录（按 object key 匹配处于上传中状态的记录）而不是新建；
认领不到时 SHALL 新建一条，接口 MUST NOT 因为记账状态而不可用。

#### Scenario: 原始文件在入口即持久化

- **WHEN** 前端完成直传但随后导入进程崩溃
- **THEN** 原始文件仍完整保留在 OSS 中，可在恢复后据 object key 重新导入

#### Scenario: 批次记录可溯源到 OSS 对象

- **WHEN** 一次导入完成（无论成功或失败）
- **THEN** 对应批次记录中包含该原始文件的 OSS object key/位置，可据此重新拉取原始文件

#### Scenario: 签发凭证即留下记录

- **WHEN** 用户在界面上选定文件、后端签发直传凭证
- **THEN** 库中已存在一条对应本次上传的批次记录，状态为「上传中」，且携带本次的 object key

#### Scenario: 落库失败则不签发凭证

- **WHEN** 签发凭证时批次记录写入失败
- **THEN** 后端返回错误、不返回凭证，用户不会开始一次服务端不知情的上传

#### Scenario: 续签凭证不新增记录

- **WHEN** 一次耗时较长的直传在传输途中多次续签凭证
- **THEN** 每次续签都返回可用的新凭证，但库中该次上传仍只有一条批次记录

#### Scenario: 续签沿用同一个 object key

- **WHEN** 前端为一次进行中的上传续签凭证
- **THEN** 后端不生成新的 object key，续签所得凭证对正在写入的那个 key 依然有效

#### Scenario: 续签仍受授权前缀约束

- **WHEN** 续签请求携带的 object key 不在本次授权的前缀内
- **THEN** 后端拒绝该请求，不签发凭证

#### Scenario: 导入触发认领已有记录

- **WHEN** 前端完成直传并凭 object key 触发导入
- **THEN** 该次上传在库中仍只有一条批次记录，其状态从「上传中」推进到排队/处理中，
  而不是新增第二条

#### Scenario: 不再执行导入后本地归档

- **WHEN** 一次导入成功完成
- **THEN** 系统不把原始文件移动到本地归档目录，OSS 对象即为原始留档

### Requirement: 上传阶段的批次状态必须会被收尾

处于上传中状态的批次记录 MUST NOT 无限期停留在该状态。后端 SHALL 周期性回收超时的上传中
批次，判据 SHALL 是「这次上传是否还有可能完成」而非固定时长：直传凭证过期后该次上传
再也无法完成，因此超时阈值 SHALL 由凭证有效期推导，MUST NOT 是一个可与凭证有效期矛盾的
独立配置项。

回收 SHALL 以对象是否真实存在为分支：

- 对象存在 → 字节已传完、只是导入未被触发。该批次 SHALL 转入排队并由既有的排队接手机制
  导入，MUST NOT 要求用户重新上传。此路径 SHALL 同样执行文件大小上限校验——否则跳过导入
  触发接口即可绕过该上限。
- 对象不存在 → 该批次 SHALL 判为失败，并给出可操作的说明（请重新上传）。

回收 SHALL 由轮询承担，MUST NOT 依赖前端在失败时回报——关标签页、进程被杀、断电这些
恰恰是本要求要覆盖的场景，而它们都不给前端执行回报的机会。

#### Scenario: 传到一半断掉的上传被判失败

- **WHEN** 一次直传中断，OSS 中不存在该 object，且已超过凭证有效期加宽限
- **THEN** 对应批次记录状态变为失败，错误信息说明上传未完成、请重新上传

#### Scenario: 传完但未触发导入的上传被自动接手

- **WHEN** 一次直传已完成（对象存在于 OSS）但导入触发接口从未被调用，且已超时
- **THEN** 该批次转入排队，由排队接手机制完成导入，用户无需重新上传

#### Scenario: 未超时的上传不被打扰

- **WHEN** 一个大文件正在直传，尚未超过凭证有效期加宽限
- **THEN** 该批次保持上传中状态，回收机制 MUST NOT 将其判为失败

#### Scenario: 绕过导入触发接口不能绕过大小上限

- **WHEN** 一个超过大小上限的对象经上传完成，但导入触发接口未被调用，由回收机制接手
- **THEN** 该批次被判为失败并说明超限，MUST NOT 被导入
