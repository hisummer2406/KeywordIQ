# 规格与指令维护约束

- 功能行为及场景写现有 openspec/specs 或批准的 delta；指令只写工作规则，不记录已实现列表、完整 API、参数副本和交付进度。
- 技术取舍维护对应 design，操作步骤复用 command/skill/runbook；纯目录导航只含链接与读取条件，不形成新的功能正文。
- 根 CLAUDE.md 目标少于 200 行；局部约束用有效 paths，避免无路径规则或 @ 导入把全部细则重新常驻。
- 不支持路径规则的 Agent 按根索引手动读；验证 YAML、glob、Git ignore 和真实代表文件覆盖，不能声称未经运行的自动加载通过。
- 一般经验两次独立事件后晋升，先查共享 Issue/OpenSpec；同次重试/复审不重复计数。高风险与用户明确长期约束首次可进，写来源。
- 审计看有效性/冲突、工具覆盖环境与跳过条件、具体反例；不能因已有测试或长期无事故删有效约束。
- 压缩/迁移列原位置与去向；用户当前批准的职责重构可执行去重与迁移，其他未批准业务行为不顺带调整。
- AGENTS 的 Code Review Rules 是专用审核投影，改语义须同步；不能把它挪成链接导致审核运行时读不到。
- 新完整变更 tasks 内联引用 Requirement/Scenario 和 design 决策，记录实现位置及实际验证；不为轻量变更虚构 spec。
- PR 合并前正向从需求查任务/实现/验证，反向从 diff 查批准范围；不能只比较两份计划或事后补 task 为额外实现授权。
- 证据对应审核 head SHA，改动后重核受影响部分；归档再查合并结果和人工验收去向，不能归档才首次审核。
- 已实现、已验证与人工待验收分开；归档不能丢未完成项，范围未兑现不关闭 Issue。
- 发布/提交/评审/合并分别按根指令与对应 command 的授权、CI 和确认条件执行，不在这里复制完整流程。
