# 评审 → 修复循环

2026-09-04 一个会话里对 PR #73/#74/#75 各走了一遍这个循环，每次都是同样九步。
这个 skill 把那九步、以及每一步真实踩过的坑写下来。

## 0. 前提

已经在这次改动的分支/worktree 里，PR 已经开着。不确定的话先看
[start-change](../start-change/SKILL.md)——那边管认领、建 worktree、合并后的三样清理，
这个 skill 不重复那些事。

## 1. 取评审内容

```bash
gh pr view --json comments          # 当前分支对应的 PR（worktree 里通常就是这个）
gh pr view <PR号> --json comments   # 显式指定
```

**本仓库的 Codex 审核走的是普通 issue 评论，不是 GitHub 正式 review**——用
`.comments`，不是 `.reviews`；后者会一直是空数组，读了当没读。

`gh api` 系列命令会不定期报 `net/http: TLS handshake timeout`，这是瞬时网络问题
（本仓库开发环境常挂代理），不是真的没有评审。**重试几次再判断"没有评论"**，
一次超时就下结论会漏掉真实存在的评审意见。

## 2. 逐条核实，不要读完意见就动手改

评审说的话是**别人对代码的一次判断**，不是代码本身。三次审核里两次指出的是真
bug，但即便是真 bug，**给出的理由也可能是反的**——一次审核纠正了自己上一轮给出
的错误推理（"空字符串会落进某个分支"，实际那个分支的条件恰好排除了空字符串）。
核实的动作是 `grep`/读实际文件，把评审提到的函数、字段、查询语句找出来亲眼确认，
不是照着评审描述的文字去改。

核实完两种结果都正常：**确认是真问题**——继续下一步；**觉得评审的理由站不住**——
去 PR 上说清楚为什么，不是默默不改也不是照单全收。

## 3. 修在根源，不是在下游垫一层

字段/排序/口径错了，优先看这个错误的**唯一事实来源**在哪一层，修那一层。三次
审核里有一条是"详情历史应该倒序，前端却按接口原样渲染"——修法是给后端查询语句
加 `.desc()`，不是让前端拿到数据后自己反转数组。理由不是"哪个更省事"，是**别处
会不会有第二个消费方**：改之前 grep 一下这个函数/字段还有没有别的调用方，只有
一个调用方（通常是刚加的这个功能本身）时，改源头没有代价；有多个调用方时，改
源头要先确认不会波及别处。

## 4. 补回归测试，并且真的验证测试有效——不是加了断言就算数

一个断言能不能抓住这个 bug，唯一的确认方式是**看着它抓住**：把修复临时撤掉（或
用等价方式还原到 bug 存在时的状态），跑一次测试，**读输出确认它真的失败了**，
再恢复修复，确认变绿。

这一步比听起来更容易出岔子，本会话真实翻过两次车：

- 用 `sed` 做多行匹配删除时，macOS 自带的 BSD sed 对某些换行语法直接报语法错误
  退出——命令失败了，文件却没被改动，而"文件没被改动"和"测试通过了"看起来是
  同一个结果。**跑完撤销/还原命令要确认它真的改了东西**（`grep` 一下改动点该有
  的痕迹在不在），不要只看返回码或想当然。
- 用 `toLocaleString()` 之类依赖运行环境时区的输出去断言具体时间字符串，本地测
  过是绿的，但 CI 的时区不一定和本地一样，断言会在别的环境上碎。这类断言优先
  换成不依赖时区的判据（比如"有没有这个字段"而不是"这个字段格式化出来是什么"），
  实在要比较时间就走带时区的 ISO 字符串或时间戳数值，不走本地化格式化输出。

## 5. 跑定向检查，全量交给门禁和 CI

只跑改动涉及的文件/用例——后端 `ruff check <改动文件>`、`pytest -k <用例名或文件>`；
前端同理只跑改动文件的 `eslint`/`vitest`。`git commit` 会触发提交门禁跑一遍相关范围
的全量检查，PR 上的 CI 还会用真库再跑一遍——这两道已经是全量的兜底，不需要在这
之前自己再跑一次全量论证"应该没问题"。

## 6. 提交

提交信息说清楚三件事：评审发现了什么、核实之后是不是真的、怎么修的。让读 diff
的人不用回去翻 PR 评论也能明白这次改动在回应什么。

**提交前看一眼这次会话对提交归属落款的要求。** 这类要求可能在会话过程中被明确
改变过，而改变之后的新提交如果还在套用旧模板，很容易被忽略——它不会报错，只会
在推送前的自查里被发现（或者更晚，被用户发现）。检查一次比事后补救省事。

## 7. 门禁没过，看懂报的是什么问题再修

门禁报的失败不是噪音，是真的检查出了问题——本会话真被 `eslint` 的
`no-promise-executor-return` 拦过一次（在竞态测试里写了个隐式返回值的 Promise
executor）。测试本身跑绿不代表 lint 也会过，两者是独立的检查，都要过。

## 8. 推送后回复审核评论

```bash
gh pr comment <PR号> --body-file <文件>
```

内容三件事：核实的结论、怎么修的、红绿验证的过程（"临时撤掉后确认真的失败，恢
复后确认通过"这句话本身值得写进回复——它是在告诉评审者这不是无脑改了就提交）。

## 9. 等 CI，报告结果

```bash
gh pr view <PR号> --json mergeable,mergeStateStatus
gh api repos/<owner>/<repo>/actions/runs -q '.workflow_runs[] | select(.head_branch=="<分支>") | .id'
```

推送会触发新一轮 CI，而这个仓库的 CI 配置了 `cancel-in-progress`——上一次推送
触发的那次 run 会被取消，这是正常行为，不是失败。**认准最新那次 run 的 id**，
轮询它到 `completed` 再汇总每个 job 的结论；查到一半 run 还没触发起来（`gh run
list` 还没反映出最新一次推送）就多等几秒再查，不要拿旧 run 的结论当新结论用。

## 循环

一次修复推送后，评审可能还会再来一轮（同一个 PR，新的评论）。回到第 1 步，同一
套流程再走一次——这正是这个 skill 存在的原因：不是走一次就结束，是每次新评论
出现都用同样的严谨程度走一遍，直到评审通过。
