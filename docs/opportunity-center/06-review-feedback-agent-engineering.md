# 机会中心 PRD 评审意见：来自 Agent 工程实践的六个补强建议

**状态：** 评审反馈
**日期：** 2026-09-05
**评审对象：** `opportunity-center-agent-workbench-prd.md` 及其 6 篇子文档
**结论：** 架构方向正确，四条关键决策（多租户、受控语义层、状态机编排、V0 数据边界）均有成熟先例支撑，建议合入。以下六条为补强建议，按优先级排序，均附带可参考的公开实践来源。

---

## 总体评价

PRD 在「安全边界」上是超配的：禁止外部写、证据门槛、不可变审计，这些在 Agent 产品中少见且正确。四大架构决策的先例验证：

| PRD 决策 | 先例支撑 |
|---|---|
| 状态机 + 禁自由循环 | 淘宝主播 Agent 用 DAG 全局规划替代 ReAct 单步决策，实测执行成功率 0.847 vs 0.737，迭代轮次 5.44 vs 8.02（《更可靠的主播助理：淘宝主播Agent的Harness工程实战》） |
| 受控语义层、禁任意 NL2SQL | 淘宝百补数据分析助手弃用 Text-to-SQL 的三大理由——幻觉字段、口径错误、不可复现——与本 PRD 的理由一致，其 NL2MDL2SQL 路径已验证可行（《淘宝百亿补贴数据分析助手 Agent 实战》，PRD 04 已引用） |
| 多专家拆分而非大而全 | 「不同 Agent 需感知的知识范围、服务范围、权限、出错代价不同，拆开后上下文相互隔离、评测可独立迭代」（《重构协同：关于AI Native团队的思考》，天猫技术团队） |
| 证据链优先于模型自觉 | 「Checker 凭证据链 Review 而非凭感觉」的对抗性设计（《对 Loop Engineering 的思考》，腾讯云开发者） |

薄弱处集中在两点：**审批的分级设计**（当前二值审批会把人变成瓶颈）与**知识资产的保鲜机制**（当前只有「启用前人工审核」，缺防腐烂设计）。以下建议 1、2 直接针对这两个缺口。

---

## 建议 1（高优先级）：审批从二值改为风险分层

**位置：** 01-product-prd.md §6、02-agent-workflow-spec.md §5

**问题。** 当前审批只有「批准/拒绝」两态。但机会中心的操作存在天然的风险谱系：只读查询无副作用，生成草稿可撤回，创建内部验证任务影响他人工作量。全部走人工审批，「审批人」会成为整个工作台的吞吐瓶颈——这正是「单点提效、全局更堵」的协同反例。

**建议。** 参照主播 Agent 的四级风险分层，把「待批准动作」按风险分级：

| 级别 | 触发条件 | 策略 |
|---|---|---|
| auto | 只读查询、证据检索、解释生成 | 直接放行，记录 trace |
| soft-gate | 有副作用但可撤回（草稿、brief、内部任务） | 会话内提示，可批量确认 |
| hard-gate | 影响他人的动作（分配验证任务、shortlist 入库） | 阻塞等待，指定审批人确认 |
| block | 外部写操作（询盘、采购、改价等 PRD 禁区） | 直接拒绝并告警——对应 PRD 现有的永久禁区 |

分级声明由工具契约承载（见 PRD 04 §2 工具契约的只读/草稿/外部写三类），框架统一执行。V0 可以只实现 auto + hard-gate 两级，但数据模型和审批实体从第一天就应记录风险级别，避免后补迁移。

**来源。** 主播 Agent 审批分层：auto（查询话术）/ soft-gate（常规切品）/ hard-gate（品类批量操作，无超时不确认不执行）/ block（平台红线）。其设计动机与机会中心相同：不能每步都确认，也不能全放行。

## 建议 2（高优先级）：给规则/指标/模板资产加保鲜机制

**位置：** 04-semantic-layer-and-tool-contracts.md §2

**问题。** PRD 对实体目录、指标字典、Signal 规则只要求「版本化」和「启用前人工审核」。但语义层资产是持续演化的：指标口径会变、外部源会失效、规则会过时。没有保鲜机制，语义层上线即开始腐烂，Agent 的结论质量随之劣化——「知识底座必须能自己活下去，靠人肉维护很快会烂掉」（《重构协同》）。

**建议。** 三项机制：

1. **有效期元数据**：每个指标定义、Signal 规则、工具契约携带 `valid_until` 与 `last_verified_at`；到期未复核的资产自动降级为「需复核」状态，Agent 引用时必须向用户显式标注。
2. **注入即记账**：Agent 每次引用语义层资产生成结论，都记录资产版本号到证据快照。资产失效时可反查受影响的结论清单——这是证据血缘（PRD 04 §2）的自然延伸。
3. **使用信号回收**：被高频引用且未引发用户纠错的资产延长有效期；持续被退回的资产触发复核。参考腾讯安全 AI 知识底座的「90 天有效期 + 自动退场复活 + 采纳率驱动」实践。

**来源。** 腾讯安全中心 AI 知识底座：准入双门禁、三层质量分级、90 天保鲜、注入即记账、主动注入代替 Agent 自搜，实现 99.7% 知识由流程自动沉淀。

## 建议 3（中优先级）：专家编排引入 Maker-Checker 对抗结构

**位置：** 02-agent-workflow-spec.md §2 角色契约

**问题。** 当前设计依赖每个专家自觉输出 `counter_conditions`（反证条件），但「自己找自己的反例」在机制上是弱的——LLM 倾向于支持自己已生成的结论。

**建议。** 把对抗关系写进角色契约的结构而非自觉：

- 机会发现专家（Maker）提出候选假设 → 市场验证专家（Checker）**必须**产出「尝试推翻该假设的证据检索记录」，无论成败均入证据包；
- 主理 Agent 调度时，对每个「建议推进」的候选强制安排一次 Checker 轮次，未经过对抗检验的候选不得进入「待决策」状态；
- 对抗记录（检索了什么、找到什么、推翻与否）写入 evidence_snapshot，成为决策者可见的「已检验」标记。

这与 PRD 03 §4 的质量门槛互补：数据质量由确定性规则守门，结论质量由对抗结构守门。

**来源。** 《对 Loop Engineering 的思考》：Maker-Checker 的 Checker 必须凭证据链质疑而非凭感觉；天猫 CodingAgent 实践中 spec-reviewer（规范审查）作为独立 Skill 与 code-generator 对置，同理。

## 建议 4（中优先级）：指标字典增加恒等式校验

**位置：** 04-semantic-layer-and-tool-contracts.md §2 指标字典

**问题。** PRD 要求指标「版本化」并列出「禁止混用的近义指标」，但没有给出口径正确性的可验证标准。指标字典一旦出错，所有下游 Signal 和结论全部带毒——这是 PRD 03 说的「错了不会报错」类缺陷。

**建议。** 参照百补指标注册表的「乘法恒等式铁律」：凡可分解的指标（如需求 = 曝光 × 转化率 × 客单价），因子相乘约分后必须恰好等于总额列，校验不通过禁止注册。对不可分解的指标（如排名、份额），要求声明「与哪些指标存在数学关系」并在 CI 中校验。这给 #7/#55 的指标定义工作提供了一个机器可查的建卡验收标准。

**来源。** 百补 MetricDef 结构：`formula_type: multiplicative`，因子约分恒等于 `total_col`，作为计算逻辑正确性的机器证据。

## 建议 5（低优先级）：复盘专家引入信任度与 Decision Trace

**位置：** 01-product-prd.md §7 V1「人工确认式偏好候选」、05-delivery-and-acceptance.md §2 基线回查

**问题。** PRD 的反馈闭环（feedback / outcome_review）记录了「采纳/忽略」，但没有把反馈转化为 Agent 行为的调节信号。V1 的「偏好候选」缺少一个从保守到自信的渐进机制。

**建议。** 引入 Decision Trace + 信任分：

- 每条 Agent 建议记录：决策点、建议内容、证据指针、用户动作（accept / reject / modify）、回查后的实际效果（lift）；
- 信任分非对称更新：采纳且效果好 +0.05，采纳但效果差 −0.10（给错建议比不给更伤信任），拒绝但 Agent 对 +0.03；
- 信任分决定输出形态：高信任直接给建议+反例+把握度，中信任给数据+弱参考，低信任只摆数据不给方向——「结论必须显示未知项」的 PRD 原则可以随信任度动态调节其强度。

**来源。** 主播 Agent 信任度自进化：trust ≥ 0.7 给 recommend，0.4–0.7 给 evidence + 弱参考，< 0.4 只给 evidence。

## 建议 6（低优先级）：长程任务采用 Reducer 状态注入替代历史回放

**位置：** 02-agent-workflow-spec.md §4「机会上下文包」

**问题。** 机会档案是长生命周期的（发现 → 验证 → 决策 → 复盘可能跨数周），「版本化的机会上下文包」方向正确，但若每次执行都从对话历史重建上下文，既贵又易漂移。

**建议。** 参照主播 Agent 的 Reducer 模式：LLM 只负责决策（产出 Action），确定性的 Reducer 函数负责状态变更；每轮执行前将最新结构化状态（当前阶段、已批准证据索引、待办任务、风险缺口）以 system-hint 注入，替代长历史回放。PRD 的「上下文包」可以直接定义为这个结构化状态的快照——事实上它与 PRD 已列的字段几乎一一对应，只需明确「由确定性函数维护、而非 LLM 重述」。

**来源。** 主播 Agent 上下文工程手段二：传统做法把工具结果全量塞进历史导致状态模糊、膨胀、不可回放；Reducer 模式让模型每轮看到干净、确定、最新的状态快照。
